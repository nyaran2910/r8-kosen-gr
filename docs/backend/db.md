# DB設計

## 保存するもの

原本ファイル → 知識要素・問題傾向の構造化データ → レビュー → 定義テーブルへ登録。

原本の全文は原本ファイルで保持し、問題文・解答・解説を丸ごとDBへ保存する中間工程は作らない。抽出結果には一般的な知識の説明、分類、対象試験との関連、出典識別情報を残す。知識の説明は自分の表現で記述する。資料利用の扱いは [legal.md](../common/legal.md) を参照。

自作・生成問題は別途キャッシュする。出題・評価・復習は大問単位。初版では小問テーブル、年度・大問番号の専用カラム、共通条件・依存関係の詳細管理は設けない。

## 最小テーブル案

以下はアプリのDBに作る予定のテーブル一覧。まだ実装済みではない。原本から抽出した定義、試験との対応、自作・生成問題を保存するための案であり、原本の問題を丸ごと保存する一覧ではない。

`exams` は学習対象を選ぶ入口。選んだ試験のIDから、対象ジャンル・形式・知識候補を取得して生成コンテキストを組み、保存済みの生成問題も取得する。

| テーブル | 保存するもの |
| --- | --- |
| subjects | 教科の定義 |
| exams | 教科まで区別した対象試験、試験区分、知識の制限設定 |
| genres | 教科内の大まかな分野と説明 |
| formats | 大まかな問題形式と説明 |
| knowledge_elements | ジャンルに属する知識の名称・Markdown本文・コスト |
| exam_genres | 試験と対象ジャンルの対応 |
| exam_formats | 試験と対象形式の対応 |
| problems | 自作・生成した大問、解答・解説、試験・形式への参照、廃止日時 |
| problem_genres | 大問と複数ジャンルの対応 |
| problem_knowledge | 生成問題と使用する知識の対応 |
| users | Googleアカウントとアプリ内ユーザーの対応 |
| user_knowledge_states | ユーザーごとの現在の知識理解度 |
| user_format_states | ユーザー・試験・形式ごとの現在の理解度 |
| attempts | 一回の演習・問題評価・形式理解度の変化 |
| attempt_knowledge_feedback | 演習ごとの知識評価・理解度の変化 |
| user_problem_review_states | ユーザー・問題ごとの現在の復習予定 |
| understanding_changes | 理解度の手動変更の履歴 |
| account_deletions | 退会処理の記録と独立台帳への書き出し状態 |
| login_registrations | Googleログイン完了通知の操作IDと処理結果 |

問題傾向はまずジャンル・形式と試験への関連で表す。専用の傾向テーブルは必要性を見て追加する。学習履歴・理解度・復習予定は上記のユーザー別テーブルで扱う。

試験は「東北大学工学部編入・数学」の単位。同じ大学の物理は別レコードにし、教科は `subject_id` で参照する。大学・学部・選抜区分の分解は保留する。

## ここまでのカラム・型案

PostgreSQLでの案。マイグレーションはまだ作成しない。

| テーブル | カラム |
| --- | --- |
| subjects | `id UUID`、`name TEXT` |
| exams | `id UUID`、`name TEXT`、`category TEXT`、`subject_id UUID` |
| formats | `id UUID`、`name TEXT`、`structure TEXT`、`answer_type TEXT`、`description_md TEXT` |
| exam_genres | `exam_id UUID`、`genre_id UUID` |
| exam_formats | `exam_id UUID`、`format_id UUID` |
| genres | `id UUID`、`subject_id UUID`、`name TEXT`、`description_md TEXT` |
| knowledge_elements | `id UUID`、`genre_id UUID`、`title TEXT`、`body_md TEXT`、`cost NUMERIC` |

`id` は主キー、参照IDは外部キー。`cost` 以外は必須とし、名称・本文・説明は空白だけにしない。ジャンルは一つの教科、知識は一つのジャンルに所属する。定義は試験ごとに複製せず、名称だけで同一と判断しない。参照中の教科・ジャンルは連鎖削除しない。

レビュー済みの定義をDBに登録し、抽出候補はレビュー用ファイルで扱う。ユーザーの理解度は知識の定義に含めない。

## コストと生成

- コストは「どのレベルの大学で出る知識か」の指標。算出方法・尺度・値は未決定。
- 未設定は `NULL` とし、0として扱わない。登録・閲覧・理解度評価は未設定でも進められるが、コスト制限を使う生成には値が必要。
- 試験ごとに「大問の合計コスト、または知識要素数の上限」と「1要素のコスト上限」を持つ案。方式・値・カラムは未確定。

生成時は対象試験の教科・ジャンル・形式から知識候補を取得し、レビューした対象知識と制限に合わせて選ぶ。ジャンル内の全知識がその試験の範囲とは限らない。生成後も参照先と制限を確認する。

形式は大問に代表形式を一つ付ける案。

## 問題形式

`formats` は生成時の指示と形式ごとの理解度評価に使う。構成 `structure`（単一設問／複数小問）と回答の種類 `answer_type`（計算／証明・説明／選択など）を持つ5カラム案は確認済み。分類の全候補・混合形式の扱いは必要な抽出例から決める。

例は「複数小問・計算中心」。この組み合わせを一つの形式として管理し、形式の定義は試験間で共有する。ユーザーの形式理解度は試験ごとに持つ。分類のための追加テーブルは作らない。

## 試験とジャンル・形式の対応（確認済み）

`exam_genres` と `exam_formats` は「この試験で何を扱うか」を記録する。各テーブルは参照IDを二つ持ち、その組み合わせを主キーにする。独立したIDは追加せず、同じ対応の重複登録を防ぐ。

例えば東北大学編入・数学に「線形代数」「微分積分」を紐づけ、対象形式に「複数小問・計算中心」を紐づける。一つの試験に複数のジャンル・形式を登録でき、同じ定義を他の試験でも使える。ジャンルは試験と同じ教科に属するものを登録する。

初版の対応には出題頻度・優先順位を追加しない。ジャンルと形式をそれぞれ紐づけるだけなので、どのジャンルでどの形式が出るかという組み合わせまでは表さない。

## 自作・生成問題のカラム案（確認済み）

`problems` は一つの大問を一レコードとして保存する。小問は問題文のMarkdown内にまとめる。

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | UUID | 問題ID・主キー |
| exam_id | UUID | 対象試験への参照 |
| format_id | UUID | 代表形式への参照 |
| body_md | TEXT | 問題文 |
| answer_md | TEXT | 解答 |
| explanation_md | TEXT | 解説 |
| retired_at | TIMESTAMPTZ | 廃止日時。未廃止はNULL |

`retired_at` 以外は必須。教科は試験から取得する。ジャンルは `problem_genres`、知識要素は `problem_knowledge` に保存し、一つの大問に複数紐づける。

レビュー済みの問題を登録し、生成途中の候補は別途扱う。問題を出題した後に内容を訂正する場合は別IDで保存し、過去の回答・復習の参照先を保つ。

## 問題とジャンル・知識要素の対応（確認済み）

| テーブル | 必須カラム | 主キー |
| --- | --- | --- |
| problem_genres | `problem_id UUID`、`genre_id UUID` | 二つのIDの組み合わせ |
| problem_knowledge | `problem_id UUID`、`knowledge_id UUID` | 二つのIDの組み合わせ |

各IDは外部キー。同じ対応の重複を防ぎ、独立したIDは追加しない。出題する問題にはジャンル・知識要素をそれぞれ一つ以上紐づける案。

ジャンルは対象試験で扱うものを選ぶ。使用知識の所属ジャンルも問題のジャンルに含める。問題ジャンルは分野別の検索、問題知識は説明の表示・理解度評価・コスト確認に使う。

## ユーザーテーブル（確認済み）

`users` はログインした人と学習履歴・理解度を紐づけるためのテーブル。

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | UUID | アプリ内のユーザーID・主キー |
| google_sub | TEXT | Googleアカウントの識別子。退会後はNULL |

`id` は必須。`google_sub` は通常は設定し、退会時にNULLへ変更する。設定済みの値を一意にする。初版はGoogleログイン専用とし、認証元カラムや別の認証用テーブルは設けない。初回ログインで作成し、以後は同じユーザーを取得する。学習データは内部の `id` に紐づける。

初版の最小案ではメールアドレス・表示名・画像を保存しない。必要になったら追加する。セッション関連テーブルは認証方式を決めてから設計する。

## 知識理解度テーブル（確認済み）

`user_knowledge_states` はユーザーごとの現在の知識理解度を保存する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| user_id | UUID | ユーザーへの参照 |
| knowledge_id | UUID | 知識要素への参照 |
| understanding | SMALLINT | 理解度。1〜5 |
| updated_at | TIMESTAMPTZ | 最後に理解度を更新した日時 |

全項目必須。ユーザーID・知識IDの組み合わせを主キーにする。行がなければ未評価とし、初回評価は3を基準に「わかった」+1／「わからない」−1。その後は保存値から更新し、1〜5に収める。

手動変更では指定した値を保存する。同じ知識の理解度は問題・試験をまたいで共有する。過去の回答評価と復習予定は別テーブルで扱う。

## 形式理解度テーブル（確認済み）

`user_format_states` はユーザー・試験・形式ごとの現在の理解度を保存する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| user_id | UUID | ユーザーへの参照 |
| exam_id | UUID | 試験への参照 |
| format_id | UUID | 問題形式への参照 |
| understanding | SMALLINT | 理解度。1〜5 |
| updated_at | TIMESTAMPTZ | 最後に理解度を更新した日時 |

全項目必須。ユーザーID・試験ID・形式IDの組み合わせを主キーにする。行がなければ未評価。初めて評価・手動設定したときだけ作成し、全形式分を事前作成しない。

同じ試験・形式の大問で理解度を共有するが、別の試験では同じ形式でも別の値を持つ。初回評価は3を基準に、完璧+2／正解+1／不正解−1／諦めた−1。結果は1〜5に収める。手動変更では指定値を保存する。

## 演習テーブル（確認済み）

`attempts` は一回の演習を記録する。同じ問題を再度解く場合は別レコードにする。

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | UUID | 演習ID・主キー |
| user_id | UUID | ユーザーへの参照 |
| problem_id | UUID | 問題への参照 |
| started_at | TIMESTAMPTZ | 表示開始通知の初回受信日時。通知前はNULL |
| answer_viewed_at | TIMESTAMPTZ | 初めて「答えを見る」を押した日時。未操作はNULL |
| submitted_at | TIMESTAMPTZ | 評価を確定した日時。未確定はNULL |
| result | TEXT | 完璧／正解／不正解／諦めた。未確定はNULL |
| closed_at | TIMESTAMPTZ | 未確定演習を終了した日時。終了していなければNULL |
| scheduled_review_at | TIMESTAMPTZ | 評価確定時に計算した復習日時。未確定はNULL |
| scheduler_version | TEXT | その演習の復習計算方式と版。未確定はNULL |

開始時にレコードを作る案。回答時間は開始から初回の解答表示操作までの差から求め、離席・中断を含む。再読み込みで開始日時をリセットしない。評価せず離脱した演習は未確定のまま残す。

問題評価と全知識の評価をまとめて確定し、理解度・復習予定も同時に更新する。同じ演習の再送信で理解度を二重更新しない。知識ごとの評価は別テーブルで記録する。

## 演習ごとの知識評価（確認済み）

`attempt_knowledge_feedback` は、演習で入力した知識ごとの評価と、その時点の理解度の変化を保存する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| attempt_id | UUID | 演習への参照 |
| knowledge_id | UUID | 知識要素への参照 |
| understood | BOOLEAN | わかった=true／わからない=false |
| understanding_before | SMALLINT | 更新前の理解度。未評価ならNULL |
| understanding_after | SMALLINT | 更新後の理解度。1〜5 |

演習ID・知識IDの組み合わせを主キーにし、同じ知識への重複評価を防ぐ。更新前以外は必須。未評価の初回は計算上3を基準にし、履歴の更新前はNULLで残す。

評価確定時に、その問題に紐づく全知識の行を保存する。評価日時・ユーザーは演習から取得する。現在の理解度を後から手動変更しても、この履歴は変えない。

## 演習の形式理解度履歴（確認済み）

大問の代表形式は一つなので、別テーブルを増やさず `attempts` に以下の2カラムを追加する。中断終了用の `closed_at` を含め全体で12カラムの構成。

| 追加カラム | 型 | 内容 |
| --- | --- | --- |
| format_understanding_before | SMALLINT | 更新前の形式理解度。未評価ならNULL |
| format_understanding_after | SMALLINT | 更新後の形式理解度。1〜5 |

未確定の演習では両方NULL。評価確定時に問題評価と一緒に保存する。初回「完璧」なら更新前NULL・更新後5。確定後の履歴は手動変更で書き換えない。

対象試験・形式は問題への参照から取得する。出題済み問題の対応は変更せず、訂正版を別IDにする方針を前提とする。

## 復習予定テーブル（確認済み）

`user_problem_review_states` はユーザー・大問ごとの現在の復習予定を保存する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| user_id | UUID | ユーザーへの参照 |
| problem_id | UUID | 問題への参照 |
| next_review_at | TIMESTAMPTZ | 次に復習候補になる日時 |
| scheduler_version | TEXT | 計算方式と版。初版は `fixed_3days_v1` |
| last_attempt_id | UUID | この予定を更新した最後の演習への参照 |

全項目必須。ユーザーID・問題IDの組み合わせを主キーにする。初めて評価を確定したときに作成し、解き直しの評価確定時に更新する。開始・解答表示だけでは予定を更新しない。

初版は評価確定日時+72時間を次回日時にする。出題処理はこの日時を参照し、復習日時の計算処理は別にする。将来の忘却曲線の方式・必要な追加状態は、その導入時に決める。

## 手動変更履歴（運用方針確認に伴う反映）

`understanding_changes` は `id UUID`、`user_id UUID`、`knowledge_id UUID NULL`、`exam_id UUID NULL`、`format_id UUID NULL`、`understanding_before SMALLINT NULL`、`understanding_after SMALLINT`、`changed_at TIMESTAMPTZ`、`expected_updated_at TIMESTAMPTZ NULL` を持つ。

知識変更は知識ID、形式変更は試験ID・形式IDを指定する。変更前は未評価ならNULL、更新後は1〜5。現在値と同時に保存し、過去の演習評価と復習予定は変えない。

問題の廃止後も既に開始した演習は継続できる。新規出題・履歴からの解き直しは止める。旧問題の履歴・復習予定は削除しない。

## 中断演習の終了（学習フロー確認に伴う反映）

`closed_at` は評価を確定せず演習を終了した場合だけ設定する。`submitted_at` と両方を設定しない。再開できる演習は両方NULLのもの。ユーザーごとに再開可能な演習を一つに制限する。終了時には問題評価・理解度・復習予定を更新せず、履歴も削除しない。新たに解く場合は別の演習IDを作る。実装は未着手。

## 演習記録の詳細確認（2026-10-11）

計測は問題表示直後の開始通知と解答表示操作の初回受信時刻の差を使い、通信遅延の誤差を許容する。予約時のstarted_atはNULL。評価確定でscheduled_review_at・scheduler_versionも履歴として保存し、現在復習状態と分ける。attemptsは12カラム。

手動操作のUUIDをunderstanding_changes.idとし、期待状態のexpected_updated_atを加えて9カラム。同値指定でも操作記録を残し、現在値・状態のupdated_atを変えない。再送照合は期待状態の競合判定より先に行い、同じ操作の結果を返す。詳細は [演習記録](../common/attempt-recording.md)。

## 退会と保持（2026-10-11確認済み）

Googleとの認証紐づけを除去し、users.idと学習データは残す。学習リセット・退会に伴う学習履歴の削除は行わない。退会したユーザーのgoogle_subはNULL。古いセッションからのアクセス拒否、明示的な再登録と内部IDの対応は認証設計で具体化する。

## 退会記録（運用確認に伴う反映）

`account_deletions` は `id UUID`（退会処理ID・主キー）、`user_id UUID`（一意・保持ユーザーへの参照）、`deleted_at TIMESTAMPTZ`、`exported_at TIMESTAMPTZ NULL` を持つ。書き出し日時以外は必須。

Google紐づけ除去と同時に記録し、リポジトリ外の退会台帳へ重複なく書き出す。書き出し失敗は再試行し、紐づけや学習データを削除前の状態へ戻さない。復元は台帳照合と紐づけ除去を完了してからログイン可能にする。

## ログイン通知の記録（認証契約確認に伴う反映）

`login_registrations` は `id UUID`（通知操作ID・主キー）、`user_id UUID`（内部ユーザーへの参照）、`issued_at TIMESTAMPTZ`、`expires_at TIMESTAMPTZ` を持つ。全項目必須。Google識別子やトークン本体を複製しない。

同じ通知の再送は元のユーザーを確認し、退会済みなら拒否する。期限切れ通知から新規ユーザーを作らない。学習APIでは登録処理を呼ばない。詳細は [認証再送](../common/auth-retry.md)。

## API認証への方針変更（2026-10-13）

初版19テーブルはユーザーが作成・適用済み。認証をFastAPIへ集約する方針に変更した。login_registrationsは旧サーバー間通知案の表なので必要性を再検討するが、今回はDBを変更しない。セッション方式の選定後、必要な変更だけをユーザーがマイグレーションで行う。
