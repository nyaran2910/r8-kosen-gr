# 登録検証の3項目

JSONの必須項目・承認条件・差分扱いはユーザー確認済み。実データ・JSON Schema実装・CLIは作らない。

## 1. JSONの必須項目

manifestは `schema_version=1`・`bundle_id` と、教科・試験・ジャンル・形式・知識・問題・関連の配列を持つ。対象がなければ配列を空にし、省略しない案。

| データ | 必須項目 |
| --- | --- |
| 教科 | id、name |
| 試験 | id、name、category、subject_id |
| ジャンル | id、subject_id、name、description_file |
| 形式 | id、name、structure、answer_type、description_file |
| 知識 | id、genre_id、title、body_file、cost |
| 問題 | id、exam_id、format_id、body_file、answer_file、explanation_file、retired_at |
| 関連 | 対応する二つの参照ID |

`cost`・`retired_at` は項目自体は必須で、未設定はnull。本文ファイルがない・ID参照がない・空白だけの名称や本文・知らない項目名は登録エラーにする。表記の誤りを黙って読み飛ばさない。

試験区分と形式分類は初版の使用値から始める。まだ決めていない分類を先に網羅的な一覧へ固定しない。

## 2. レビュー承認の条件

approvedにするには、レビュー者・日時と、確認したファイル一覧・ハッシュが必要。内容・数式解答・知識の紐づけ・原本表現の持ち込み確認を全て終えていることを条件にする。

取得元や作成方法が不明な場合は不明と記録する。登録や提供の可否に関わる未確認事項は、承認したことにせず保留する。一般的な参考情報の未記入と、利用に必要な根拠不足を同じ扱いにしない。

CLIでは承認状態とハッシュの一致を確認するが、人のレビューを自動で代行しない。承認後にJSON・本文・画像・根拠記録を変えた場合は再レビューする。

## 3. 再登録時の差分

| 状況 | 扱い |
| --- | --- |
| 同じID・同じ内容 | 変更なし。重複作成しない |
| 新しいID | 新規登録候補として表示 |
| 既存定義の名称・説明の修正 | 差分を表示し、意味が変わらない修正だけ明示して反映 |
| 問題内容・使用知識・試験・形式の変更 | 同じIDでは拒否。訂正版を別IDで作る |
| ファイルからレコードを削った | DBから自動削除しない |
| 問題の廃止 | 廃止日時の変更を運用操作として明示し、履歴は残す |

一つの登録単位に不正な項目があれば全体を止め、半分だけ登録しない。複数の登録単位は依存先から順に登録する。エラーには対象ファイル・レコードID・項目を示す。
