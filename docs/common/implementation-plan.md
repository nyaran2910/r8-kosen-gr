# 実装計画

更新日：2026-10-07

## 1. この計画の目的と使い方

現在の要件を、実際に着手できる作業単位に分解する。まずassetsの東北大学過去問を初期キャッシュとして登録し、そこから形式・知識要素を抽出して学習が一巡するアプリを作る。その後に出題の調整、AIによる教材作成、抽出作業のシステム化へ進む。

- 要件の基準は [requirements.md](./requirements.md)、採用技術の基準は [tech-stack.md](./tech-stack.md) とする。
- この文書の「確定」はユーザーが指定した内容、「案」は実装を進めるための提案である。案を決定したら、その決定を該当節に記録する。
- チェックボックスは実装・確認が終わった時点で更新する。計画を書いただけでは完了にしない。
- 各段階の完了条件を満たしてから次へ進む。ただし、教材の手作業での作成は起動基盤の準備と並行できる。
- コード、コマンド、パス、API名は現時点の設計案であり、既に存在する機能ではない。
- 日数の見積もりはまだ置かない。最初の一巡を実装してから、実際の作業量を基に見積もる。

現状、`apps/` は空で、アプリの実装は始まっていない。`implementation-plan.md` を作ったことと、アプリが実装済みであることを区別する。

## 2. 目標と実装範囲

### 2.1 初版で実現すること

1. ユーザーがログインする。
2. 登録済みの問題から、そのユーザー向けの問題を選ぶ。
3. 問題を読み、答えを見る操作で解答・解説を確認する。
4. 問題や解説から知識要素を開き、関連する知識を辿る。
5. 元の問題へ戻る。
6. 問題全体と知識要素ごとの評価を入力する。
7. 評価、経過時間、回答日時、理解度の変化を保存する。
8. 保存した情報を次の出題に反映する。
9. 自分の理解度と過去の回答履歴を確認・編集する。

最初はパソコンで使える画面を対象にする。教材と問題はユーザー間で共有し、理解度・回答履歴・出題状態はユーザーごとに分離する。

### 2.2 初版完成後に進めること

- AIによる教材・問題の事前生成と、人間の確認を経た登録。
- 初期教材の準備を超える、過去問や参考資料からの知識要素・試験傾向の抽出システム。
- 抽出結果を確認して承認する仕組み。
- pgvectorによる類似問題・関連知識の検索。
- 学習者に合わせた実行時のAI問題生成とキャッシュ再利用。
- 出題パラメータをユーザーが手動指定する機能。

これらは初版の学習動線を作った後に着手する。最初の学習動作を確認するために、AI接続やベクトル検索を必須にしない。

## 3. 確定しているルール

### 3.1 理解度の更新

知識要素・試験の出題形式に対する理解度は1〜5で管理する。

| 評価対象 | 入力 | 更新量 |
| --- | --- | --- |
| 知識要素 | わかった | +1 |
| 知識要素 | わからない | -1 |
| 問題に紐づく試験の出題形式 | 完璧 | +2 |
| 問題に紐づく試験の出題形式 | 正解 | +1 |
| 問題に紐づく試験の出題形式 | 不正解 | -1 |
| 問題に紐づく試験の出題形式 | 諦めた | -1 |

更新は `更新後 = min(5, max(1, 更新前 + 更新量))` とする。例えば、形式理解度4で「完璧」と評価した場合は5、知識理解度1で「わからない」と評価した場合は1になる。

初回評価までは「未評価」として扱い、理解度3とは区別して表示する。初回のみ3を計算基準にし、知識は「わかった」で4、「わからない」で2、形式は「完璧」で5、「正解」で4、「不正解／諦めた」で2になる。2回目以降は保存済みの理解度から増減する。

問題全体の評価で、知識要素の理解度を自動的に追加更新しない。知識理解度は知識要素ごとの入力、形式理解度は問題全体の入力から更新する。

### 3.2 ログインとデータの分離

- 初版からログイン必須。
- Googleアカウントによるログインを使用する。認証ライブラリとセッションの管理方式は未決定。
- Googleアカウントがあれば誰でも利用でき、初回ログイン時にアプリ内のユーザーを作成する。
- 学習データの所有者は、APIが認証情報から判定する。
- ブラウザーから送られた任意のユーザーIDを所有者として信用しない。
- 他人の回答履歴、理解度、出題状態を閲覧・更新できないことを確認する。
- ログアウト後は、以前のユーザーの情報が画面に残らないようにする。

### 3.3 教材と時刻

- 問題・解答・解説・知識の本文はMarkdownテキストとしてDBに保存する。
- 本文から画像、数式、通常のリンク、知識へのリンクを扱えるようにする。
- 教材の関連付けやユーザーの学習データは通常のテーブルで管理する。
- JSONBは追加メタデータなど必要な箇所に限る。本文をJSONの独自構造へ変換することは初版の前提にしない。
- 保存する時刻はUTCの `timestamptz`、画面上の表示はAsia/Tokyoとする。

## 5. 段階1：開発環境と起動基盤を作る

### 5.1 ディレクトリ構成案

```text
apps/
  web/                     # Next.js / TypeScript
  api/                     # FastAPI / Python
    app/
      api/                 # HTTP入出力・認証依存
      models/              # SQLAlchemyモデル
      schemas/             # 入出力型
      services/            # 評価保存・理解度更新・問題選択
      cli/                 # 教材検証・登録
    migrations/            # Alembic
    tests/
assets/
  seeds/                   # 東北大学過去問の登録メタデータ・抽出結果（案）
  sources/                 # 既存の参考資料
compose.yaml
.env.example
```

- [ ] 抽出する形式の粒度と知識要素の粒度を確認してから、他の問題へ広げる。
- [ ] 同じ知識を年度・問題ごとに重複作成せず、共有する安定IDへ紐づける。
- [ ] 抽出した知識の説明と関連を確認し、承認後にDBへ登録する。
- [ ] 一つの大問で取り込みと表示が確認できたら、両年度の残りの問題を登録する。

初期教材のための抽出・確認は段階3で行う。抽出・レビューを汎用のシステムにする開発は段階11に残す。画像など対象教材に含まれない表現の描画確認が必要なら、確認専用データを公開キャッシュとは分けて用意する。

### 7.2 登録形式案

本文は `.md` ファイルで編集し、登録時にDBのテキスト列へ保存する。ID、教科、知識の関連、本文ファイルのパスなどのメタデータはJSONで渡す案とする。JSONを画面へ表示するのではなく、Markdown本文を描画する。

- [ ] 知識・問題・試験・形式の登録形式を定義する。
- [ ] ファイル参照先と画像参照先の基準ディレクトリを決める。
- [ ] 必須項目、ID重複、関連先の存在、本文の空欄を検証する。
- [ ] 知識リンクの規則を決める。例：`[方程式](/knowledge/<安定ID>)`。
- [ ] 本文のリンクと `problem_knowledge` を別に扱う。出題対象の知識を本文のリンクだけから推測しない。
- [ ] DBへ書き込まず検証だけ行うモードを用意する。
- [ ] 登録中の失敗で中途半端な教材が残らないようにする。
- [ ] 同じ教材の再登録を、更新・無視・エラーのどれにするか決める。
- [ ] 問題の更新時には版と履歴の扱いを確認する。
- [ ] 件数と検証結果を、対象ID・ファイル位置が分かる形で表示する。

**完了条件：** 小さな教材セットを再現可能な手順で登録でき、壊れた関連を含む教材は登録前に検出できる。

## 8. 段階4：ログインとユーザー分離を実装する

認証は学習データの保存より先に完成させる。

- [ ] 段階0で選んだ認証方式に合わせて、ログイン・ログアウトを実装する。
- [ ] 初回のGoogleログイン時にアプリ内のユーザーを作成し、次回以降は同じユーザーへ紐づける。同時ログインでも重複作成しない。
- [ ] ログイン状態と現在のユーザーを取得できるようにする。
- [ ] API側でもログイン必須を検証する。画面へのアクセス制御だけで済ませない。
- [ ] セッションの期限切れを扱う。
- [ ] Cookieを使うなら、HttpOnly・Secure・SameSiteと、更新APIのCSRF対策を構成する。
- [ ] ログイン失敗・期限切れ・通信失敗を区別して表示する。
- [ ] ブラウザーからAPIへ送る認証情報を定義する。
- [ ] Webの中継がある場合、偽造可能なユーザーIDヘッダーを認証の代わりにしない。
- [ ] ログアウト・別アカウントへの切り替えでユーザー依存のキャッシュを消す。
- [ ] 確認用の二つのアカウントを用意する。

**確認方法：** 未ログインのAPI呼び出しを拒否する。二人のアカウントで切り替え、同じ教材を共有しながら個人データが混ざらないことを確認する。

**完了条件：** APIが現在のユーザーを一貫して判定でき、ログインを迂回した学習データの取得・更新ができない。

## 9. 段階5：問題・解答・知識を閲覧できるようにする

### 9.1 APIの最小構成案

| 操作 | API案 | 主な応答 |
| --- | --- | --- |
| 現在のユーザー | `GET /me` | ユーザーの識別情報 |
| 知識一覧 | `GET /knowledge` | ID、タイトル、自分の理解度・未評価状態 |
| 知識詳細 | `GET /knowledge/{id}` | Markdown本文、関連、自分の理解度 |
| 指定問題の取得 | `GET /problems/{id}` | 問題本文、関連知識。解答はここで返さない |
| 演習の開始 | `POST /attempts` | 演習ID、開始時刻、問題本文 |
| 演習の取得・再開 | `GET /attempts/{id}` | 所有者の演習状態、許可された表示内容 |
| 解答の表示 | `POST /attempts/{id}/reveal` | 解答・解説、最初の表示時刻 |

APIの戻り値とエラーの形を先に決める。教材がない場合、非公開の場合、演習が他人のものの場合を区別して処理する。

### 9.2 画面と操作

- [ ] ログイン後の入口画面を作る。
- [ ] 知識一覧と知識詳細を作る。
- [ ] 問題画面と「答えを見る」ボタンを作る。
- [ ] 共通のMarkdown描画部品を作り、問題・解説・知識で使用する。
- [ ] インライン数式と独立した数式の表示を確認する。
- [ ] 画像の読み込みと表示サイズを確認する。
- [ ] 生のHTML・危険なURLをどう扱うか決め、本文から任意のスクリプトを実行できないようにする。
- [ ] 知識リンクを、画面内の詳細表示または独立ページへ接続する。
- [ ] 知識を複数回辿っても、元の問題・演習IDへ戻れるようにする。
- [ ] 戻った時に解答の表示状態と入力途中の評価を保持する。
- [ ] ブラウザー更新で別の演習を勝手に作らないようにする。
- [ ] 読み込み中、教材なし、取得失敗、リンク先なしの表示を用意する。

**完了条件：** ログイン後、問題→解説→知識→別の知識→元の問題の操作ができる。途中で戻ったり再読み込みしたりしても演習の状態が破綻しない。

## 10. 段階6：評価保存と理解度更新を実装する

### 10.1 演習の状態

初版の案は「開始済み→解答表示済み→評価確定済み」とする。

- 問題表示を計測の開始とする。演習作成時刻と混同せず、表示開始をサーバーへ通知する方法と通信遅延の扱いを実装時に決める。
- 初めて「答えを見る」を押した時点を計測の終了とする。解答取得の待ち時間・解説閲覧・評価入力の時間は含めない。初回の終了時刻だけを保存し、再表示で書き換えない。
- 評価確定時に問題全体の評価、知識ごとの評価、確定時刻を保存する。
- 回答時間は問題表示から初回の解答表示操作までの経過時間とする。離席・中断を含め、同じ演習の再開・再読み込みで開始時刻をリセットしない。時刻の記録方法は実装時に揃える。
- 確定済みの演習を再送信しても、理解度を二重に増減しない。

### 10.2 保存API案

`POST /attempts/{id}/feedback` に問題評価と知識評価を送る。ユーザーIDや更新後の理解度をクライアントに決めさせない。

保存処理は次の順に行う。

1. 演習がログインユーザーのものか確認する。
2. 演習が評価可能な状態か確認する。
3. 問題評価が許可された四つの値のどれか確認する。
4. 知識評価が演習に関連する知識だけを対象としているか確認する。
5. 必須の知識評価の不足・重複を確認する。
6. 現在の知識・形式理解度を取得する。
7. 決定済みの増減ルールを適用し、1〜5に収める。
8. 評価、更新前後の理解度、演習の確定状態を一つのトランザクションで保存する。
9. 更新後の値と確定結果を返す。

### 10.3 作業と確認

- [ ] 知識の二択入力と問題全体の四択入力を作る。
- [ ] 未入力の知識を画面で示し、すべての知識評価が揃うまで保存できないようにする。APIでも不足を検証し、不完全な評価では履歴・理解度を更新しない。
- [ ] 保存中・保存成功・保存失敗を表示する。
- [ ] 保存失敗時は入力を残して再試行できるようにする。
- [ ] 連打・通信再送・二つのタブからの確定でも一回だけ更新する。
- [ ] 同じユーザーの別演習が同時に保存されても、理解度の更新を失わないようにする。
- [ ] ロックや一意制約など、同時実行の制御方法を選ぶ。
- [ ] 形式に紐づかない問題は、形式理解度を更新せず評価・知識更新を保存する。
- [ ] 記録中に例外が起きた場合、履歴だけ・理解度だけが残らないことを確認する。
- [ ] 初回評価と上下限の処理を確認する。

**重要なテスト例：** 4から完璧で5、1から不正解で1、知識2からわかったで3。同じ演習を二回送っても最初の結果と同じ。他人の演習への保存は失敗する。

**完了条件：** 一回の演習の評価が一回だけ保存され、履歴と知識・形式理解度が矛盾しない。ここでM3の中核が完成する。

## 11. 段階7：履歴と理解度の確認・手動編集を実装する

### 11.1 履歴

- [ ] `GET /history` で自分の確定済み演習を新しい順に取得する。
- [ ] 問題名、問題評価、回答日時、経過時間を表示する。
- [ ] 件数が増えても取得できるようにページ分割する。
- [ ] 履歴詳細で問題・解説・知識評価・理解度の変化を確認できるようにする。
- [ ] 問題が更新されても、当時の版の表示方針に従って履歴を確認できるようにする。
- [ ] 未確定の演習を確定済み回答と混ぜない。

### 11.2 理解度の確認と編集

- [ ] 知識一覧・詳細で自分の理解度を表示する。
- [ ] 問題の傾向・形式の確認画面を用意し、試験・教科ごとの形式と自分の形式理解度を表示する。
- [ ] 未評価と理解度1〜5を区別する。
- [ ] 知識要素の確認画面から知識理解度を、問題の傾向・形式の確認画面から形式理解度を、1〜5の範囲で直接設定できるようにする。APIでも範囲と更新対象のユーザーを検証する。
- [ ] 手動変更の時刻と理由を記録するかを決め、採用した方針を実装する。
- [ ] 手動変更で過去の回答評価を書き換えない。
- [ ] 手動設定直後の出題に新しい値が反映されることを確認する。
- [ ] 保存済みの理解度を画面に反映し、古い表示が残らないようにする。

**完了条件：** ユーザーが自分の履歴と理解度を確認でき、知識・形式それぞれの確認画面から理解度を編集できる。他人のデータは一覧・詳細・更新のどの経路からも扱えない。

## 12. 段階8：ユーザー別の出題と復習を実装する

最初は動作を説明できるルールで作る。選択ロジックを画面やDBアクセスから分け、後から差し替えられるようにする。

### 12.1 候補の絞り込み案

1. 公開済みで、必要な本文と関連が揃った問題を対象にする。
2. 初版で決めた対象試験・教科に絞る。
3. 未回答の問題と、ユーザー別の次回復習日時が現在時刻以前になった問題を候補にする。
4. 次回復習日時に達していない回答済み問題は候補から外す。
5. 候補がない場合は、その状態を画面に返す。未実装のAI生成へ進まない。

### 12.2 優先順位の初期案

- 最初は未評価の知識を含む問題を優先し、学習状態を集める。
- 次に、関連知識の理解度が低い問題を優先する。
- 次に、そのユーザーの形式理解度が低い問題を優先する。
- 条件が同じなら、最後の回答日時が古い問題を優先する。
- 最後まで同条件なら安定IDなどで順序を決め、確認時の再現性を確保する。

複数知識の集約は最低理解度を使う案とする。この順位は確定要件ではない。実際に数件の履歴で挙動を確認し、必要に応じて変更する。

### 12.3 実装作業

- [ ] 現在時刻を入力として渡せる選択関数を作る。
- [ ] 復習日時を計算する処理と、候補の絞り込み・優先順位の処理を分離する。出題側は次回復習日時を参照し、3日という値を直接持たない。
- [ ] 初版の計算方式を固定間隔方式として実装する。次回復習日時は回答確定時刻+設定値の3日（72時間）とする。
- [ ] 計算処理への入力は評価・回答確定時刻・過去の復習状態、出力は次回復習日時・計算方式と版を基本にする。履歴参照が必要な方式も追加できるようにする。
- [ ] 回答確定時に復習状態も同じトランザクションで更新する。重複送信や同時保存で予定が二重更新・逆行しないようにする。
- [ ] 復習間隔の設定と出題の優先順位を、それぞれ一か所で定義する。
- [ ] 知識理解度・形式理解度・最終回答日時を取得する。
- [ ] `POST /attempts/next` などで、選択と演習開始を接続する。
- [ ] ブラウザー更新では既存演習を再取得し、次の問題の開始と区別する。
- [ ] 選択理由を開発時に確認できるようにする。
- [ ] 出題結果に他人の理解度・履歴が混ざらないようにする。
- [ ] 候補がない時に、知識一覧や履歴へ移動できるようにする。

### 12.4 確認例

- 初回利用者には未回答の問題が出る。
- 同じ教材でも、理解度が異なる二人には優先順位が変わる。
- 同じ知識理解度なら、形式理解度の低さが順位へ反映される。
- 直後に回答済み問題へ戻らず、復習間隔を越えると候補へ戻る。
- 日付境界はUTCの経過時間で判断し、表示上の日本時間と混同しない。
- 教材がない場合と、教材はあるが候補がない場合を扱える。

**完了条件：** ユーザー別の学習状態で出題が変わり、回答済み問題が時間経過で再び候補になる。実際の日時を数日待たずに検証できる。

### 12.5 将来の忘却曲線への対応

- 初版では忘却曲線のモデルを実装しない。固定間隔の計算処理を、将来の計算処理へ置き換えられることを確認する。
- 問題評価、回答日時、知識評価、理解度の変化は履歴として保持する。次回復習日時だけでは過去の学習過程を再現できないため、履歴を予定で上書きしない。
- 具体的なモデル、必要な状態、問題単位か知識単位かの復習対象は、拡張時に決める。未知のパラメータ用の列を先回りして大量に作らない。
- 新しい計算方式へ移行するときは、既存予定を維持して次の回答から適用するか、履歴から再計算するかを決める。計算方式・版の記録により区別できるようにする。
- 固定間隔では、72時間の直前は候補外、ちょうど72時間で候補になることを確認する。計算処理の差し替え確認では、出題側を変更せず異なる次回復習日時を扱えることを確認する。

## 14. 段階10：AIによる教材の事前生成を追加する

アプリが既存教材で動くようになってから、教材を増やす作業を支援する。

1. 人間が知識ID、対象試験・形式、作問条件を指定する。
2. 生成用CLIからAIへ依頼する。
3. 問題・解答・解説とメタデータを下書きファイルへ保存する。
4. 登録CLIと同じ形式検証を行う。
5. 人間が内容を確認・修正する。
6. 承認した版だけを登録する。

- [ ] 生成結果と公開済み教材を分離する。
- [ ] 使用モデル・生成条件・生成日時・入力の版を記録する。
- [ ] APIキーはサーバーまたはCLIだけで扱う。
- [ ] 失敗時の再試行と重複生成を扱う。
- [ ] 正しい形式でも、内容の正しさが保証されるわけではないため人間の確認を挟む。
- [ ] 生成した問題で既存の閲覧・評価・出題が動くことを確認する。

AIの具体的なモデル・SDK・費用は、この段階で公式情報を確認して決める。現時点では固定しない。

**完了条件：** AI生成を使っても、未確認の教材がそのまま学習者へ公開されない。

## 15. 段階11：外部資料の抽出とレビューを追加する

### 15.1 抽出

- [ ] 対象資料・対象範囲・出典情報を指定する。
- [ ] 知識要素、関連、試験傾向、形式を分けて抽出する。
- [ ] 下書きとして保存し、公開DBへ直接登録しない。
- [ ] 重複しそうな知識と、参照先が不明な関連を提示する。
- [ ] 元資料と抽出結果を比較できる形にする。

### 15.2 レビューと登録

- [ ] 承認・修正・却下の状態を持つ。
- [ ] 誰が何を確認したかを残す。
- [ ] 修正後も形式検証と関連先の確認を行う。
- [ ] 承認済みの結果だけを、既存の登録処理で取り込む。
- [ ] 取り込み後の知識リンクと出題の関連を確認する。

レビュー画面の開発に入る前に、少量の下書きをファイルでレビューして、必要な操作を確認する。

**完了条件：** 抽出→レビュー→承認→登録の流れが分かれ、確認途中の情報が学習画面へ混ざらない。

## 18. 次に着手する具体的な作業

最初の作業は次の順に進める。

1. 段階0の初期値・認証方式・時間定義を決める。
2. 技術スタックに残る匿名セッションの記述をログイン方針に合わせる。
3. Web・APIの最小プロジェクトを作る。
4. ComposeでWeb・API・PostgreSQLを起動する。
5. DB設計と最初のマイグレーションを作る。
6. 東北大学過去問の一つの大問を登録対象にし、形式・知識要素の抽出結果と登録CLIを用意する。
7. ログイン後に一つの問題と知識を表示する。
8. 解説表示、評価保存、履歴確認までをつなぐ。

一回の変更は「起動できる」「教材を登録できる」「評価が保存できる」など、動作で確認できる単位にする。各変更で、変更内容・確認手順・残る制限を記録する。
