# 要件定義書

## 基本の要件

- ユーザーが触るwebアプリを作る。とりあえずパソコンでみる。初版はDB・API・フロントエンドを全てローカル起動する。
- 教材からアプリむけに問題やらを整理するシステムを構成する。とりあえず優先度は低いのでアプリ側ができたら。
- 原本の完全な内容は原本ファイルで保持し、丸ごとDB化する中間工程は作らない。
- 東北大学の過去問は抽出元として使い、原本の問題文・解答・解説をアプリDBや初期問題キャッシュへ転載しない。原本から知識要素・形式・出題傾向の構造化データを直接抽出し、レビュー後に登録する。
- 出題・問題全体の評価・復習は自作・生成した大問単位で行う。知識要素の評価は、大問に紐づく要素ごとに行う。

## 機能要件

### アプリ内で実現する機能

#### ログイン機能

- 初版からアプリの利用にはログインを必要とする。
- ログインにはGoogleアカウントを使用する。認証・内部ユーザー登録・セッション・本人確認はFastAPI側で管理し、Next.jsは表示と中継を担当する。
- Googleアカウントがあれば誰でも利用できる。初回ログイン時にアプリ内のユーザーを作成する。
- 学習データはログインしたユーザーに紐づけて保存し、出題や学習状況の表示に使用する。
- アカウント削除ではGoogleの認証紐づけを除去するが、内部ユーザーIDと学習データは保持する。学習データの削除リセットは初版に設けない。
- 退会後の古いセッションは拒否する。同じGoogleで再登録した場合は新しい内部IDを作り、旧学習データを自動で引き継がない。
- 将来のAI学習・研究への活用は別途具体化し、初版で自動転用する処理は設けない。

#### 知識要素の確認機能

- 知識要素を一覧機能
  - 要素が一覧で表示されて、その内容を確認できる。
  - どれかの知識要素をタップするとその詳細が見れて、その知識の説明や例が乗っている。
  - さらにその知識要素、例えば2次方程式の解の公式とかで、さらに"方程式"って単語が説明にあるとして、別の知識要素として、方程式があったらそこにそこがリンクみたいになってて、その方程式という知識要素にすぐに飛べる感じ。
  - わからない単語があったらどんどんその知識要素を辿れる感じ。
  - 自分の学習データも見て、その要素の理解度がデータとしてどう設定されてるかも見れる。知識要素の確認画面から、自分の理解度を1〜5で直接変更できる。
  - 理解度も表示される

#### 問題の傾向・形式の確認機能

- 試験・教科ごとの問題の傾向や形式を確認できる。
- その確認画面から、各出題形式に対する自分の理解度を1〜5で直接変更できる。
- 知識・形式の理解度の手動変更は現在の学習状態に反映し、過去の回答評価は書き換えない。

#### 問題をときまくる機能

- 出題機能
  - 出題をユーザーの知識要素の理解度、試験の問題の形式ごとの得意不得意などを鑑みて出題を行う機能。
  - 出題時、過去に解いて、数日経ったりしたものは自動で出題候補になる。
  - 初版では前回の回答確定から3日後に復習候補へ戻す。間隔は設定値として管理する。
  - 将来は忘却曲線に基づく復習間隔へ拡張する。復習日時の計算を出題候補の選択から分離し、回答履歴を使う方式へ差し替えられる構成にする。具体的なモデル・計算式は後で決める。
  - 答えを見るボタンを押したら回答・解説が見れる

- ユーザーフィードバック機能
  - ユーザーが問題を解いたとき、その諸情報を記録し、今後の出題ロジックに反映する的な。
  - かかった時間など自明なものは自動で記録
  - 回答時間は、問題を表示してから初めて「答えを見る」を押すまでの経過時間とする。解説閲覧・評価入力の時間は含めず、途中の離席や中断は含める。実作業時間とは区別する。
  - 解答後にその問題で用いられた知識要素ごとに「わかった／わからない」を入力させ、理解度を1〜5の五段階で更新する。「わかった」は1上昇、「わからない」は1減少とする。
  - 解答確認後、大問に紐づくすべての知識要素への二択評価を必須とする。未入力の要素がある場合は評価を保存できない。
  - 問題全体として「完璧／正解／不正解／諦めた」の4段階を入力させ、記録する。その問題に紐づく試験の出題形式への理解度を、次のルールで更新する。
    - 完璧：2上昇。
    - 正解：1上昇。
    - 不正解：1減少。
    - 諦めた：1減少。
  - 知識要素・出題形式の理解度は、更新後も1〜5の範囲に収める。
  - 知識要素・出題形式は、初回評価まで「未評価」として扱い、理解度3とは区別して表示する。初回評価時のみ3を基準に増減し、2回目以降は保存済みの理解度から増減する。

- 回答確認機能
  - 問題を解いた後、操作によって回答を確認できる。
  - 知識要素の確認と同じように、説明や解答に含まれる知識要素があったら、その文字をリンクみたいにタップするとその知識要素を参照できる。
  - そこの画面は知識要素一覧画面と共通化してよくて、同じ操作できるみたいな。で、すぐに問題にももどれるUIもある的な。
  - 出題機能のユーザが答えを見るボタンを押したら発動する感じ。

- 問題傾向の選択機能
  - アルゴリズムに完全に出題を任せるか、ユーザーが手動で問題の一部のパラメータを決めるかをユーザーが選択できる
  - 初版ではやらない

- AI問題生成機能
  - ユーザの学習データから適切な問題を生成する。もしくはそれに近しい問題がすでにデータベースに登録されている場合はそれを出題する。
  - 判定はアルゴリズムと生成AIを組み合わせる感じ？それともアルゴリズムのみ？もちろん問題を生成する際は、受けたい資格の範囲やユーザーが苦手だと考えられる分野などをAIが参照していい感じにフォーマットに沿った回答を作成する。
  - これはできたら出題次に勝手にキャッシュから持ってこれるか、生成する必要があるかを判断する感じでユーザーに意識させない。
  - 初版ではとりあえずキャッシュ問題から出すのでこれは実装しない。

#### 自身の学習状況を確認できる機能

- 学習データの確認
  - 過去回答した問題の状況の履歴が見れる

- ユーザーごとの学習状況表示の分離
  - 自分のデータしか基本見れないし、出題に反映されるパラメータも自分の状況のみになる。

### アプリ外で用意したい昨日というかシステムというか仕組み (他の仕組みができたらこれに取り掛かる。優先度は低い。)

- 知識要素抽出機能
  - 過去問や参考書等からその分野の知識を小さめの単位で抽出していく機能。
  - 生成AIで抽出し、DBに入れやすいよう、一定の形式でまとめていく。
  - 例) ２次方程式の解の公式みたいな感じ。
  - まだデータベースには突っ込まない。

-  問題の傾向や範囲の抽出機能
  - 過去問や参考書等から目標とする大学や資格の問題を生成する際に必要な諸々の情報を抽出する機能。

- 人間のレビュー
  - 問題傾向や知識要素を一定の形式で抽出した後、DBにぶち込む前に人間がレビューをできる仕組み
  - ここで承認済みになったらDBに突っ込む感じ。

### データベースで保存しておくもの

- 知識要素
  - 各知識要素に「どのレベルの大学で出題される知識か」の指標としてコストを割り当て、その要素の定義に保存する。算出方法・尺度・具体的な値は今後決める。コスト制限を使う生成に利用する承認済み知識では値を必須とする。対象大学向けの大問には、合計コストまたは要素数の上限と、1要素のコスト上限を設定できるようにする。初版案では試験に設定を持たせる。方式・単位・数値は未決定。
  - それぞれの知識要素を例とかと一緒に保存しておく。
  - 画像やリンク、数式などとにかくmdで記述できるものは全て保持できるようにしたいなー。っていうかmdファイルとして保存してもいいかも。
  - 関連する知識へのリンクもあり、そのリンクが貼られる文字にはmd記法の[リンクだよ](url)みたいにやる感じ。

- 問題の傾向とか形式
  - 大学ごとの傾向やその資格の問題の傾向や形式などを保持しておく。
  - 大学ごとというより試験の種類で区別する感じ。英検1級、東京大学高専編入試験みたいな感じ。
  - 試験は「東北大学工学部編入・数学」のように教科まで区別した別テーブルにし、教科テーブルを参照する。問題は試験を参照する。
  - 教科・ジャンル・形式・知識要素は再利用できる定義として、それぞれのテーブルに保存する。問題ごとに定義を複製しない。
  - 抽出した定義をレビュー後に登録し、試験と対象ジャンル・形式を紐づける。生成時は対象試験から定義と知識候補を拾い、説明と制限をコンテキストに入れる。
  - 初版は項目を減らす。年度・大問番号の専用カラム、共通条件・小問間の依存関係の構造化は不要とする。最小案は大問のみの問題テーブルとし、小問は本文に残す。
  - 形式は構成（単一設問／複数小問）と回答の種類（計算／証明・説明／選択など）を持つ。分類の全候補・混合形式の扱いは未決定。細かな小問別の回答形式・解法パターンの分類は必須にしない。
  - 初版案では大問に代表形式を一つ紐づける。形式理解度はユーザー・試験・形式ごとに保存し、大問全体の評価で更新する。知識要素は複数紐づけ、要素ごとの二択評価で更新する。
  - 最小テーブル案と未決定事項は [DB設計メモ](../backend/db.md) にまとめる。

- ユーザーの学習データ
  - ユーザごとに知識要素の理解度を五段階で保存。
  - 問題の回答状況、かかった時間、答えた日、それに紐づく知識要素、答えた問題がもし特定の試験に紐づくならその試験のその形式に対しても得意不得意を5段階くらいで保存する。
  - ユーザごとに用意する感じ。それぞれの知識要素と紐づいて、知識要素ごとの覚えてる度合いが保存される。あと試験オブジェクトが保存する形式にも理解度が紐付く感じ。

- 問題のキャッシュ
  - 毎度毎度問題を生成してたらAPI代が敵わないので、生成した問題はキャッシュしておき、問題を生成する際に似たような境遇の人間が同じような問題を生成してたらそれを使わせる感じのキャッシュ。
  - 問題の本体はもちろん、キャッシュヒットをさせるための諸々の情報も保持する。
