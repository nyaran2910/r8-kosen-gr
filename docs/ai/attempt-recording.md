# 演習記録と再送の詳細案

[ユーザー向け案](../common/attempt-recording.md) はユーザー確認済み。コード・DB実装は行わない。

## 予約と開始通知

問題選択・演習予約はPOST。既存のユーザーごと未確定演習一つの条件は予約も含む。`started_at` をNULL可とする新提案。POST /attempts/{id}/startが最初の通知を受けたサーバー日時を保存する。再送は同じ時刻。GETでは計測開始せず、解答表示は開始後のみ。予約中に終了することは可能とする。予約が残れば次回はその演習を開き開始通知を送る。

表示開始からサーバー受信までと、答えを見る操作からサーバー受信までの遅延差が記録時間の誤差になる。解答応答待ち・評価入力は含めないが、答えを見る要求の送信失敗で受信が遅れた場合は誤差が大きくなる。実作業時間・厳密な操作時間と同一とはしない。通知失敗を隠して計測完了扱いにせず再試行を案内する。研究で精密な計測が必要なら別途計測設計を見直す。

started_atがNULLの場合、answer_viewed_at・submitted_at・result・形式変化・復習計算結果はNULL。終了はclosed_atを持てる。開始した演習は解答表示操作受信後にだけ評価を確定できる。開始後の再読み込みでは通知で初回時刻を上書きしない。

## 復習計算結果

`attempts.scheduled_review_at TIMESTAMPTZ NULL` と `attempts.scheduler_version TEXT NULL` を追加する案。評価確定と両項目の非NULLを一体にし、履歴・現在理解度・現在復習状態と同じトランザクションで保存する。再送はここに残る値を返す。過去方式の再計算に依存しない。追加すればattemptsは12カラム。カラム追加とstarted_atの必須性変更は今回承認後に概要へ反映する。

## 手動設定の操作識別

既存の `understanding_changes.id` は入力操作のUUIDにする案。`expected_updated_at TIMESTAMPTZ NULL` を追加し、9カラムとなる。期待状態が未評価ならNULL。知識または試験形式という対象キー、指定理解度、期待更新日時を保存済み操作と照合する。本人と対象が同じ操作ID再送では、現在状態が後から変わっていてもその操作の保存済み結果を返す。別内容や他人のIDは拒否する。

同値指定も操作レコードを残す方針へ変更する新提案。before=afterは変更なしを表す。状態行のupdated_atは変更せず、changed_atは操作を受け付けた日時。UIでは実質変更と同値指定を必要に応じ区別する。独立した再送管理テーブルを増やさない。未評価に値を設定する操作では状態行を新規作成する。

通常は操作IDの再送照合を先に行い、未処理なら期待更新日時を検証して状態行と操作レコードをまとめて保存する。同時要求は対象状態を直列化し、行未作成も一意制約で競合を処理する。履歴の演習評価を手動設定の操作履歴へ混ぜない。

## その他の実装前詳細

API中継タイムアウトは10秒を初期設定案とし、読み取り要求は必要なら再試行するが更新の自動再試行は同じ操作IDでのみ行う。時計はUTC、APIのタイムアウト・JWT期限と演習時間を混同しない。鍵配置や配信画像・描画ライブラリは別途具体化する。登録・根拠ファイルの公開範囲は未決定のまま。
