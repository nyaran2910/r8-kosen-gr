# 認証通知と競合の内部契約案

[今回の3項目](../common/auth-retry.md) はユーザー確認済み。コード・マイグレーションは作らない。

## 登録表明と結果

POST /auth/google/completeはNext.jsのGoogle成功callbackからのサーバー間通知だけを受ける案。署名表明のaudを通常APIから分け、RS256、iss、purpose、jti（操作UUID）、Google主体、iat、expを検証する。expはiat+60秒を上限とし、未来の発行日時や期限切れを拒否する。Next.jsの同一Googleログイン成功処理の再送は同じjtiと同じ発行情報を使う。通常のAPI JWTはsub=内部ID、google_subと通常API audienceを使い、この経路に流用しない。

login_registrationsはid UUID主キー（jti）、user_id UUID必須外部キー、issued_at TIMESTAMPTZ必須、expires_at TIMESTAMPTZ必須を提案。登録処理は操作IDの重複と時刻、usersの非NULL google_sub一致を確認する。既存操作なら紐づくユーザーだけを返す。紐づくユーザーが退会済み・claim不一致なら拒否し、Google識別子から新ユーザーを作り直さない。

新規操作なら現在有効なgoogle_subのusersを取得し、なければ新UUIDを作成し、操作記録と同時に確定する。同時ログインの異なるjtiでもgoogle_subの一意制約でユーザー重複を防ぐ。同じjti・違うGoogle主体の衝突はユーザー情報を返さず拒否する。発行日時・期限の違う再送も同一操作と認めない。

操作記録は期限経過後なら拒否を保証できるため後で整理可能だが、具体的な清掃は初版に必須化しない。token全体やGoogle主体をこの記録に複製しない。退会前にAPIで成功した登録操作の再送を拒否する仕組みであり、未処理の別Googleログイン完了通知まで自動で旧ユーザーに紐づけることはしない。新規のログイン完了通知は新登録になり得る。発行元はGoogle成功を確認したサーバーのみで、ブラウザーや古い通常セッションに新しい登録通知を発行させない。

## 同時処理と退会再送

更新処理は署名を検証した上でusers行を対象に直列化し、google_sub一致をロック下で再確認する。学習の保存・退会完了の順序で結果を決め、学習データはどちらの順序でも削除しない。user状態の確認と更新を別トランザクションで行って退会後の書き込みを許可しない。

DELETE /meは操作UUIDを持ちaccount_deletions.idへ保存する。署名が有効だがgoogle_subが既にNULLの場合、この経路だけ同じ内部ID・同じ退会操作IDの記録が存在すれば元の完了結果を返せる案。通常の学習APIでは例外を作らず拒否する。異なる退会操作IDのNULLユーザーは認証拒否。アカウントを復活させず、他人の退会記録も開示しない。

退会再送に使う署名表明が期限切れなら再送で新しく登録をしない。Next.jsが同じ旧セッションから退会結果確認用の限定表明を発行できる場合も通常の学習操作を許可しない設計とし、最終的な画面復帰はログアウト状態へ導く。初版の実装でこの経路が複雑になる場合は、認証拒否時にログアウトし台帳で処理済みを確認する運用へ縮小することをユーザーに共有する。

## エラー・再試行

token_expiredとsession_expired、account_detached、invalid_signature等を機械判定用codeで分ける。署名不正・主体不一致の理由を過度にクライアントへ詳細開示しない。Next.jsが再発行するのはtoken_expiredだけで、自分のAuth.jsセッションが有効な場合の一回まで。payload・演習ID・操作IDは維持し、確定済みの結果照合をAPI側で行う。

この3項目の承認後、現行API・DB・認証文書へ反映する。具体的な署名ライブラリや並行トランザクションの実装・検証は認証段階で実施する。基本設計の確認は実装開始指示ではない。
