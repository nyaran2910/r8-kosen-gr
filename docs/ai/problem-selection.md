# 出題ルールの詳細コンテキスト

[ユーザー向け案](../common/problem-selection.md) はユーザー確認済み。実装しない。

## 選択処理

現在時刻・対象試験・認証済みユーザーを入力とし、対象問題と状態を取得する。未確定演習の再開確認を先に行う。出題可能性は後続の問題廃止・レビュー設計と整合させる。登録・関連・本文・解答・解説が揃った問題を使い、廃止問題を出題しない。

復習状態なしを未確定問題と扱い、状態があれば `next_review_at <= now` を候補条件にする。通常は評価確定と復習状態更新を同じトランザクションで行うため状態が対応する。確定履歴があるのに復習状態がない場合は未回答と無条件に扱わず、整合性不良として修復・確認する。

順位は復習グループが先。復習グループでは予定日時が古い順、同時刻の場合のみ未評価知識・低理解度・形式・IDの基準を使う。新規グループでは未評価知識の有無、評価済み知識の最低理解度、形式の未評価・理解度、IDの順を使う。未評価知識数で優劣を付けない。評価済み知識が一つもない場合の最低値は順位計算上5とし、全部未評価だから苦手と決めつけない。未評価表示や初回評価の計算基準3は変えない。

知識の最低値は手動変更後の現在値も参照する。形式は同じ試験の現在値。復習日時は手動変更だけでは変えない。未評価と評価済み3を一つの数値で扱わず、それぞれの順位条件を持つ。単純な初版ルールであり最適性・忘却モデルを主張しない。

## 手動解き直しと中断後

履歴閲覧は演習作成なし。解き直しボタンでは本人の過去演習の問題から新しい演習を作り、本文を表示する。問題が廃止されていれば履歴は閲覧できても解き直しは不可とする案。中断演習があれば先に再開または終了を選ぶ。

中断演習の終了後の除外は次回の自動選択一回だけに限定し、他人や他のユーザーの出題に影響させない。永続的な出題拒否リストを追加しない。直前に終了した演習の問題IDをサーバーの本人確認済み状態から取得する実装案はAPI設計時に詰める。

手動解き直しは理解度・予定を通常と同じく更新するため、早い解き直しで予定も72時間先へ延びる。この振る舞いもユーザー確認対象。候補不足を理由に期限前問題を自動出題したりAI生成に切り替えたりしない。

## 検証すべき設計例

期限直前は候補外・ちょうど期限で候補、複数復習は古い予定が先、未評価有無が同条件なら低理解度が先、知識の条件が同じなら形式の苦手が先、全知識未評価でも順位が決まる、本人の状態だけを参照、中断終了後の除外で同じ問題が続かない、手動の期限前解き直しは予定を更新する、履歴閲覧では更新しない。これらは後の実装検証用で、今回はテストコードを作らない。
