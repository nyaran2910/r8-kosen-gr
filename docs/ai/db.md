# DB設計の詳細コンテキスト

ユーザー向けの現行概要は [DB設計](../backend/db.md) を参照する。以下は設計の詳細・制約・未決定事項。

## 方針

初版は少ない項目で始め、実験・運用に合わせて変更する。以前の小問別テーブル・共通条件・依存関係の詳細設計は初版の必須要件から外す。登録・出題・評価・復習は大問単位とする。

年度・大問番号は専用カラムにしない。原本の問題文・解答・解説は抽出元として扱い、アプリDBへ転載しない。抽出根拠として出典のURLや識別情報を記録する。小問の独立テーブルは必要性が分かってから検討する。

## 原本からの登録フロー

原本ファイル → 知識要素・問題傾向の構造化データ → レビュー → 定義テーブルへ登録

原本の完全な内容は原本ファイルで保持する。問題文・解答・解説を丸ごと別のDBへ保存する中間工程は作らない。DBに残すのは抽出した定義・対象試験との関連・出典識別情報。問題傾向は、現行のジャンル・形式と試験への関連で表し、専用テーブルの必要性は後で判断する。自作・生成問題のキャッシュは別用途として扱う。

## 抽出データ・対象試験・生成問題のテーブル案

以下はカラム確定前の最小案。抽出結果は再利用できる定義として保存し、問題キャッシュから参照する。

| テーブル | 役割 | 主な項目案 |
| --- | --- | --- |
| subjects | 教科の定義 | ID、名称 |
| exams | 教科まで区別した対象試験 | ID、名称、教科ID、知識の制限設定 |
| genres | 教科内の大まかな分野 | ID、教科ID、名称、説明 |
| formats | 大まかな問題形式の定義 | ID、名称、説明 |
| knowledge_elements | 共有する知識要素 | ID、ジャンルID、名称、Markdown本文、コスト |
| exam_genres | 対象試験で扱うジャンル | 試験ID、ジャンルID |
| exam_formats | 対象試験で扱う形式 | 試験ID、形式ID |
| problems | 自作・生成した大問のキャッシュ | ID、試験ID、形式ID、問題文、解答・解説、出典参照（必要な場合） |
| problem_genres | 大問の複数ジャンル | 問題ID、ジャンルID |
| problem_knowledge | 大問で使う知識要素 | 問題ID、知識ID |

試験は「東北大学工学部編入・数学」のような単位にする。表示用の名称は一つの文字列でよいが、教科は `subject_id` で別テーブルを参照する。同じ大学の物理は別の試験レコードにする。問題側は `exam_id` を持ち、教科を重複して保存しない。

大学・学部・選抜区分をさらに別テーブルやカラムへ分解することは初版では保留する。既存の学習履歴・理解度・復習用テーブルは別途必要。

## 教科・ジャンルテーブルの最小カラム・型案

### subjects（教科）

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| id | UUID | 必須 | 主キー。名称変更でも変えない安定ID |
| name | TEXT | 必須 | 数学・物理などの名称。空白だけの名称は不可 |

### genres（ジャンル）

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| id | UUID | 必須 | 主キー。名称変更でも変えない安定ID |
| subject_id | UUID | 必須 | `subjects.id` への外部キー |
| name | TEXT | 必須 | 線形代数・微分積分などの名称。空白だけの名称は不可 |
| description_md | TEXT | 必須 | ジャンルの範囲を説明するMarkdown。生成コンテキストにも使う。空白だけの説明は不可 |

初版ではジャンルは一つの教科に属し、知識要素は一つのジャンルを参照する。例は「数学 → 線形代数 → 固有値」。ジャンルの階層や複数教科・複数ジャンルへの所属は、必要になってから追加する。

定義は大学・試験ごとに複製しない。試験の対象ジャンルは `exam_genres` で指定する。名称の表記揺れは取り込み時に確認し、名前だけで同一の定義と判断しない。名称への一意制約は現時点では付けない案とする。参照中の教科・ジャンルの削除は外部キーで拒否し、関連する知識を連鎖削除しない。

## 知識要素テーブルの最小カラム・型案

`knowledge_elements` の最小構成を具体化する。以下はPostgreSQLでの案であり、マイグレーションはまだ作成しない。

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| id | UUID | 必須 | 主キー。名称を変更しても変えない安定ID |
| genre_id | UUID | 必須 | `genres.id` への外部キー。初版は一つのジャンルに属する |
| title | TEXT | 必須 | 知識要素の名称。空白だけの名称は不可 |
| body_md | TEXT | 必須 | 説明・数式・例・関連リンクを含むMarkdown本文。空白だけの本文は不可 |
| cost | NUMERIC | 未設定可 | どのレベルの大学で出題される知識かを表す指標。未設定はNULL |

コストの尺度が未決定なので、整数・小数のどちらも扱える `NUMERIC` を仮の型案とし、桁数・範囲は算出方法と合わせて決める。NULLは0と区別し、コスト制限を使う生成には未設定の知識を使用しない。初期過去問の整理・閲覧・理解度評価はコスト未設定でも進められる。

教科はジャンルから取得し、知識要素に重複して保存しない。タイトルだけで同一知識と判断したり、一意制約を付けたりせず、取り込み時に定義の内容を確認する。ユーザーごとの理解度はこのテーブルに入れず、`user_knowledge_states` に保存する。

この案ではレビュー済みの定義を登録し、抽出候補はレビュー用ファイルで扱う。レビュー状態・作成日時・更新日時などの追加カラムは、必要になった段階で検討する。

## 試験テーブルの最小カラム・型案

ユーザー確認済みの最小案。試験は教科まで区別し、初版は以下の4カラムから始める案。試験区分の追加はユーザー要望に基づく。

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| id | UUID | 必須 | 主キー。表示名を変更しても変えない |
| name | TEXT | 必須 | 「東北大学工学部編入・数学」などの表示名。空白だけは不可 |
| category | TEXT | 必須案 | 大学入試・編入学・司法試験などの大まかな区分。空白だけは不可 |
| subject_id | UUID | 必須 | `subjects.id` への外部キー |

`exams` は学習対象の選択、試験に紐づくジャンル・形式・知識候補の取得、生成コンテキストの組み立て、生成問題の取得に使う。`category` は一覧の絞り込み用で、教科・ジャンル・問題形式とは別の分類。初版では文字列を提案し、区分一覧・表記は未確定。区分固有の説明や管理が必要になれば別テーブルへの参照に変更する。区分だけで出題範囲・難易度・コスト上限を決めない。

同じ大学でも数学・物理は別の試験レコードにする。大学・学部・選抜区分の分解と年度カラムは追加しない。名称だけで同一試験と判断せず、名称の一意制約は現時点では付けない案。参照されている教科・試験の削除は拒否し、問題・学習履歴を連鎖削除しない。

コスト制限は試験に設定する方針を維持するが、方式・尺度が未決定なのでカラム名・型・値を先に固定しない。制限が未設定でも抽出定義の整理・閲覧・評価は進められる。マイグレーション・初期データの作成はまだ行わない。

## 大まかな形式

### 最小カラム・型案（ユーザー確認済み）

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| id | UUID | 必須 | 主キー。名称変更でも保持する |
| name | TEXT | 必須 | 「複数小問・計算中心」などの名称 |
| structure | TEXT | 必須 | 単一設問／複数小問など、構成の分類 |
| answer_type | TEXT | 必須 | 計算／証明・説明／選択など、回答の分類 |
| description_md | TEXT | 必須 | 構成・回答の特徴を説明するMarkdown |

文字列は空白だけを許可しない。分類の全候補や計算と証明の混合形式は未確定で、取り込み時にレビューする。既存の原本を無理に単一の回答分類へ当てはめない。構成・回答分類の別テーブルは作らず、管理や説明の独立が必要になってから検討する。

一つの構成・回答分類の組み合わせを一つの形式として管理する。組み合わせの一意制約は分類の表記と粒度が確定してから検討し、取り込み時に重複候補を確認する。ジャンル・解法は形式の分類に混ぜない。大問の代表形式は一つとする案を維持する。

定義は試験ごとに複製せず、`exam_formats` で関連づける。参照中の形式は削除を拒否し、問題・理解度を連鎖削除しない。形式に教科・ジャンルへの参照を追加する必要性は保留する。

形式理解度はユーザー・試験・形式ごとに1〜5で保持する。同じ試験の同じ形式に属する大問で共有し、従来の「完璧+2／正解+1／不正解-1／諦めた-1」を適用する。確認画面から直接変更できる。

## 試験と定義の対応テーブル案（ユーザー確認済み）

| テーブル | 必須カラム | 主キー |
| --- | --- | --- |
| exam_genres | `exam_id UUID`、`genre_id UUID` | `(exam_id, genre_id)` |
| exam_formats | `exam_id UUID`、`format_id UUID` | `(exam_id, format_id)` |

各IDは対応する定義テーブルへの外部キー。独立IDを持たず、組み合わせの主キーで重複登録を防ぐ。参照されている試験・ジャンル・形式の削除は拒否する案。対応行を外しても定義や問題・理解度・履歴を連鎖削除しない。

試験とジャンルの教科一致は登録処理で確認する案（通常のID外部キーだけでは教科一致を保証しない）。対応を外した後の既存問題の出題扱いは、出題処理の設計時に確認する。

各試験に複数のジャンル・形式を登録でき、定義は複数試験から共有する。初版は出題頻度・優先順位を追加しない。二つの対応テーブルではジャンルと形式の組み合わせまでは限定できないため、生成時には選択した組み合わせの妥当性をレビューする。組み合わせを正確に指定する必要が出たら設計を見直す。

## 自作・生成問題の最小カラム・型案（ユーザー確認済み）

| カラム | 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| id | UUID | 必須 | 主キー |
| exam_id | UUID | 必須 | `exams.id` への外部キー |
| format_id | UUID | 必須 | `formats.id` への外部キー。代表形式一つ |
| body_md | TEXT | 必須 | 大問全体の問題文・小問の順序を含むMarkdown |
| answer_md | TEXT | 必須 | 解答のMarkdown |
| explanation_md | TEXT | 必須 | 解説のMarkdown |

本文・解答・解説は空白だけを許可しない。解答と解説を別カラムにすることで画面から個別に提示できる。教科・コスト・ユーザー理解度は重複保存しない。問題のジャンルは `problem_genres`、知識は `problem_knowledge` で複数参照する。

登録時には試験とジャンルの教科一致、`exam_genres`・`exam_formats` の対応、使用知識の妥当性を確認する。対応の確認を複合外部キーで保証するか登録処理で保証するかは実装時に決める。複数ジャンルを扱う方針はユーザー確認済み。

レビュー済みの自作・生成問題のみ登録する案。抽出元の原本全文や原本を再現するデータは登録しない。原本の出典情報は抽出根拠側で保持し、問題側の出典参照は必要性が出た段階で設計する。生成履歴・レビュー状態・日時などの追加項目は現時点では固定しない。

出題後の本文・解答・解説・形式・知識の変更で学習履歴の意味が変わらないよう、訂正版は別の問題IDとして扱う案。学習履歴が参照する問題の削除は拒否する。廃止・訂正版への対応や出題対象から除外する仕組みは履歴・出題処理の設計時に確認する。DB実装は未着手。

## 問題とジャンル・知識要素の対応案（ユーザー確認済み）

| テーブル | 必須カラム | 主キー |
| --- | --- | --- |
| problem_genres | `problem_id UUID`、`genre_id UUID` | `(problem_id, genre_id)` |
| problem_knowledge | `problem_id UUID`、`knowledge_id UUID` | `(problem_id, knowledge_id)` |

外部キーはそれぞれ `problems.id`・`genres.id`・`knowledge_elements.id` を参照する。重複対応は主キーで拒否する。参照中の問題・ジャンル・知識の削除は拒否する案。学習履歴がある問題の対応を変更しない。訂正版は別問題IDにする。

出題可能な問題にはジャンル・知識を各一つ以上紐づける案。最低件数は通常の外部キーだけでは保証できないため、問題と対応をまとめて登録する処理で検証する。問題の対象ジャンルは試験の `exam_genres` に含まれ、使用知識の所属ジャンルは `problem_genres` に含まれることを確認する。ジャンルと知識の対応が不整合なら登録せずレビューへ戻す。

`problem_genres` は問題の検索・表示、`problem_knowledge` は関連知識の表示、全使用知識への必須評価、重複しない知識IDによるコスト・要素数の確認に使う。利用者別の理解度や評価結果はここに保存しない。

## ユーザーの最小カラム・型案（ユーザー確認済み）

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| id | UUID | 必須 | アプリ内部の主キー。学習データから参照する |
| google_sub | TEXT | 必須 | Googleアカウントの主体識別子 |

`google_sub` に一意制約を付け、文字列は空白だけを許可しない。初回ログイン時に作成し、次回は同じ内部IDに対応させる。同時ログインで重複作成しない登録処理が必要。メールアドレスを識別キーにしない。

初版はGoogle専用として `users` に `google_sub` を直接持たせる。ユーザー指示により `auth_provider` は省く。別のGoogle認証用テーブルも初版では設けない。複数の認証元・アカウントへの対応が必要になった段階で別テーブルを検討する。メール・表示名・画像は現時点では保存を要求しない。セッション・トークン保管の方式は認証ライブラリ選定時に決める。

登録・取得はサーバーで検証した認証主体を使う。クライアントから送られた任意のユーザーID・主体識別子を認証として信用しない。認証方式によってアダプターが必要とするテーブル・カラムが追加される可能性があり、この案だけで認証設計完了とはしない。DB実装は未着手。

## 知識理解度の最小カラム・型案（ユーザー確認済み）

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| user_id | UUID | 必須 | `users.id` への外部キー |
| knowledge_id | UUID | 必須 | `knowledge_elements.id` への外部キー |
| understanding | SMALLINT | 必須 | CHECKで1〜5に制限する |
| updated_at | TIMESTAMPTZ | 必須 | サーバーが設定する理解度の最終更新日時 |

主キーは `(user_id, knowledge_id)`。初回評価・手動設定で行を作り、未評価は行の不存在で表す。ログイン時に全知識の行を3で作らない。初回の二択評価だけ3を基準に増減し、以降は保存値から増減する。結果は1〜5に収める。未評価への手動設定では指定値をそのまま保存する。

知識は共有定義なので理解度も同一ユーザー・知識なら問題や試験をまたいで共有する。試験ID・問題ID・コスト・過去の回答評価はこのテーブルに持たない。手動変更は現在値のみ変更し、過去の回答評価を書き換えない。回答確定時の評価履歴との同時保存・再送防止・同時更新は演習テーブルと合わせて設計する。

`updated_at` は手動変更でも更新されるため、最終演習日時や忘却曲線の基準として単独で使わない。演習・評価履歴や復習状態を別に保存して将来の計算方式へ対応する。ユーザーの特定は検証済みの認証情報から行う。参照中の知識の削除は拒否する案。退会時のデータ削除方針は別途検討する。

## 形式理解度の最小カラム・型案（ユーザー確認済み）

| カラム | 型 | 必須 | 内容・制約 |
| --- | --- | --- | --- |
| user_id | UUID | 必須 | `users.id` への外部キー |
| exam_id | UUID | 必須 | `exams.id` への外部キー |
| format_id | UUID | 必須 | `formats.id` への外部キー |
| understanding | SMALLINT | 必須 | CHECKで1〜5に制限する |
| updated_at | TIMESTAMPTZ | 必須 | サーバーが設定する最終更新日時 |

主キーは `(user_id, exam_id, format_id)`。未評価は行の不存在で表し、初回評価または手動設定時に作成する。初回評価だけ3を基準に、完璧+2・正解+1・不正解−1・諦めた−1を適用し、結果を1〜5に収める。以後は保存値から増減する。手動設定では指定値を保存する。

同じ試験の同じ形式なら大問間で共有する。形式定義は試験間で共有するが理解度は試験別。問題全体の評価で更新し、知識評価からは更新しない。対象試験と形式の対応を登録処理で確認する案。`exam_formats` から対応を外しても保存済み理解度や過去の履歴は削除しない。対応から外れた形式の表示・手動変更の扱いは画面設計時に確認する。

知識理解度と同じく `updated_at` は最終演習日時とは別。復習予定・過去の問題評価・更新理由は別テーブルで記録する。回答確定時の同時保存・重複確定防止・同時更新を演習テーブルと合わせて設計する。認証済みユーザーの状態だけ取得・更新する。

## 演習テーブル（ユーザー確認済み）

`attempts` は一回の演習を記録する。同じ問題を再度解く場合は別レコードにする。

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | UUID | 演習ID・主キー |
| user_id | UUID | ユーザーへの参照 |
| problem_id | UUID | 問題への参照 |
| started_at | TIMESTAMPTZ | 表示開始通知の初回受信日時。通知前はNULL |
| answer_viewed_at | TIMESTAMPTZ | 初めて「答えを見る」を押した日時。未操作はNULL |
| submitted_at | TIMESTAMPTZ | 評価を確定した日時。未確定はNULL |
| result | TEXT | 完璧／正解／不正解／諦めた。未確定はNULL |
| closed_at | TIMESTAMPTZ | 未確定演習を終了した日時。終了していなければNULL |
| scheduled_review_at | TIMESTAMPTZ | 評価確定時に計算した復習日時。未確定はNULL |
| scheduler_version | TEXT | その演習の復習計算方式と版。未確定はNULL |

開始時にレコードを作る案。回答時間は開始から初回の解答表示操作までの差から求め、離席・中断を含む。再読み込みで開始日時をリセットしない。評価せず離脱した演習は未確定のまま残す。

問題評価と全知識の評価をまとめて確定し、理解度・復習予定も同時に更新する。同じ演習の再送信で理解度を二重更新しない。知識ごとの評価は別テーブルで記録する。

### 演習の詳細制約・後続設計

`id`・`user_id`・`problem_id` は必須。`started_at` は開始通知前だけNULL。参照IDは外部キー。`result` は許可された4値に制限し、`submitted_at` と同時に設定する。解答表示済みの演習だけ評価を確定でき、時刻は開始≦解答表示操作≦確定を検証する。時刻の計測・通知と通信遅延の扱いは実装時に決める。解答取得完了時刻と操作時刻を混同しない。

未確定の状態は日時・結果のNULLから判別し、独立したstatusカラムは初版では追加しない案。経過秒数は時刻差から求める。離脱は「諦めた」と自動評価せず、未確定のまま残す。同じ演習の再開と新規演習の区別は画面・API設計時に決める。

出題済み問題の内容・試験・形式・知識の対応を変えず訂正版を別IDにする既存案を前提に、試験・形式は `problem_id` から取得する。教材の変更を許可する設計へ変える場合は当時の対応の保存を再検討する。形式理解度の更新前後は下記の `attempts` への2カラム追加案で確認する。

確定操作・評価履歴・現在の理解度・復習状態は一つのトランザクションで保存する。再送・同時確定を演習IDで制御し、二重更新を防ぐ。履歴のあるユーザー・問題の削除方針は別途決める。現段階はカラム案のみで実装未着手。

## 演習ごとの知識評価（ユーザー確認済み）

`attempt_knowledge_feedback` は、演習で入力した知識ごとの評価と、その時点の理解度の変化を保存する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| attempt_id | UUID | 演習への参照 |
| knowledge_id | UUID | 知識要素への参照 |
| understood | BOOLEAN | わかった=true／わからない=false |
| understanding_before | SMALLINT | 更新前の理解度。未評価ならNULL |
| understanding_after | SMALLINT | 更新後の理解度。1〜5 |

演習ID・知識IDの組み合わせを主キーにし、同じ知識への重複評価を防ぐ。更新前以外は必須。未評価の初回は計算上3を基準にし、履歴の更新前はNULLで残す。

評価確定時に、その問題に紐づく全知識の行を保存する。評価日時・ユーザーは演習から取得する。現在の理解度を後から手動変更しても、この履歴は変えない。

### 知識評価履歴の詳細制約

`attempt_id` と `knowledge_id` はそれぞれ `attempts.id` と `knowledge_elements.id` への外部キー。主キーは `(attempt_id, knowledge_id)`。更新前の値はNULLまたは1〜5、更新後は必須かつ1〜5。NULLを3として保存せず未評価だったことを保持する。評価がfalseでも上限・下限により変化しないケースがあるため、更新前後だけから入力内容を推測しない。

演習の問題に実際に紐づく全知識について、不足・余分・重複を登録処理で検証する。演習確定・知識評価履歴・現在理解度・形式理解度・復習状態は同じトランザクションで更新する。確定済み演習の再送は二重更新しない。理解度の更新前後はサーバーが確定時の現在状態から計算し、クライアントに決めさせない。

未確定の入力候補をこのテーブルに履歴として保存しない案。手動変更後や他の演習後でも履歴の更新前後は書き換えない。知識要素の本文が変わる場合の定義の版管理は後続検討事項。形式理解度の更新前後は下記の `attempts` への追加案を参照する。

## 演習の形式理解度履歴（ユーザー確認済み）

大問の代表形式は一つなので、別テーブルを増やさず `attempts` に以下の2カラムを追加する案。

| 追加カラム | 型 | 内容 |
| --- | --- | --- |
| format_understanding_before | SMALLINT | 更新前の形式理解度。未評価ならNULL |
| format_understanding_after | SMALLINT | 更新後の形式理解度。1〜5 |

未確定の演習では両方NULL。評価確定時に問題評価と一緒に保存する。初回「完璧」なら更新前NULL・更新後5。確定後の履歴は手動変更で書き換えない。

対象試験・形式は問題への参照から取得する。出題済み問題の対応は変更せず、訂正版を別IDにする方針を前提とする。

### 形式理解度履歴の詳細制約

`attempts` は追加2項目を含む9カラムとして確認済み。未確定では両方NULL。確定時は更新後を必須として1〜5に制限し、更新前はNULLまたは1〜5。更新前NULLは未評価を意味し、演習の `submitted_at` で未確定と区別する。

対象は `attempts.user_id` と、参照問題の試験・形式から決める。更新前後は確定時の現在状態からサーバーで計算し、演習・全知識評価・現在の理解度・復習状態と同時保存する。初回のみ計算上3を基準とし、履歴にはNULLを保持する。限界値で増減しなくても `result` を保持する。

将来問題の形式が複数になる場合や、出題済み問題の試験・形式を変更する場合は、更新対象を別途保存する設計へ見直す。現在は問題の対応を不変にする既存案を前提に重複する試験ID・形式IDを追加しない。手動変更の履歴は別途検討し、確定演習は書き換えない。

## 復習予定テーブル（ユーザー確認済み）

`user_problem_review_states` はユーザー・大問ごとの現在の復習予定を保存する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| user_id | UUID | ユーザーへの参照 |
| problem_id | UUID | 問題への参照 |
| next_review_at | TIMESTAMPTZ | 次に復習候補になる日時 |
| scheduler_version | TEXT | 計算方式と版。初版は `fixed_3days_v1` |
| last_attempt_id | UUID | この予定を更新した最後の演習への参照 |

全項目必須。ユーザーID・問題IDの組み合わせを主キーにする。初めて評価を確定したときに作成し、解き直しの評価確定時に更新する。開始・解答表示だけでは予定を更新しない。

初版は評価確定日時+72時間を次回日時にする。出題処理はこの日時を参照し、復習日時の計算処理は別にする。将来の忘却曲線の方式・必要な追加状態は、その導入時に決める。

### 復習予定の詳細制約

主キーは `(user_id, problem_id)`。各参照IDは外部キー。`last_attempt_id` は同じユーザー・問題の確定済み演習であることを登録処理で検証する。計算方式と版は一つの識別子にまとめる最小案とし、空白だけは許可しない。予定は初回の評価確定時だけ新規作成し、全ユーザー・全問題分を事前作成しない。

日時は演習の `submitted_at` を基準にサーバーが計算し、予定更新と評価確定を同じトランザクションで保存する。再送では更新せず、同じユーザー・問題の同時確定は直列化して確定時刻順の予定を保持する。過去演習の遅延した処理で最新予定を上書きしない。

行がない問題は未確定演習しかないか未演習であり、復習予定未作成として扱う。行があり `next_review_at <= 現在日時` なら復習候補。候補になっただけでは予定を書き換えず、次の評価確定で更新する。手動の理解度変更では初版の復習予定を自動変更しない案。

計算入力は演習の評価・確定日時・過去の復習状態を基本とし、必要なら履歴参照を追加できるようにする。現在の予定は履歴の代わりではない。移行時に既存予定を維持するか再計算するかは新方式導入時に確認する。先回りして未知の忘却曲線パラメータの列を追加しない。検索用索引は出題処理の実装時に検討する。

## 知識要素のコストと対象ごとの制限

各知識要素に `cost` カラムを持たせる。尺度が決まるまでは値をNULLにでき、コスト制限を使う生成では値の設定を必須とする。試験や問題ごとに同じ知識のコストを重複定義せず、知識要素の定義に保存する。コストは「どのレベルの大学で出題される知識か」を表す指標とする。ユーザーの理解度とは別に保存する。算出方法・尺度・具体的な値は今後決め、現段階では仮の数値を割り当てない。

大学ごとの制限を扱えるようにする。初版案では対象大学・教科を表す試験レコードに設定を置く。同じ大学の複数試験で共通設定を継承する仕組みは必要になった時点で追加する。

| 制限設定案 | 内容 |
| --- | --- |
| 大問あたりの知識の上限 | 知識コストの合計、または知識要素数で制限する。どちらを採用するかは未決定 |
| 1要素のコスト上限 | 大問に含めてよい各知識要素の最大コスト |

合計コスト・要素数は重複しない知識IDで計算する。生成時に候補を絞り、生成後も実際の紐づけが制限内か検証する。抽出・レビュー中の候補はコスト未設定でもよいが、コスト制限を使う生成に利用する承認済み知識にはコストの割り当てを必須とする。コスト未設定の要素を0として扱わない。制限の数値が未決定でも、レビュー済み定義の登録・閲覧・理解度評価は進められる。

原本は解析資料として扱うため、生成問題のコスト制限に合わせて原本を改変しない。

## 原本と抽出データの境界

原本 → 知識要素・教科・ジャンル・形式・試験ごとの出題傾向を構造化 → レビュー → 定義テーブルへ登録、という流れにする。問題文を保存するための中間テーブルは不要。原本ファイルの公開・削除はこの設計変更では行わない。

知識の説明は一般的な概念を自分の表現で記述し、原本の文章・解説・図や具体的な設問を再現する詳細データを抽出結果に持ち込まない。出題傾向は試験のジャンル・形式への関連と説明で表し、専用テーブルが必要かは後で決める。`problems` は抽出用ではなく、自作・生成問題を出題・復習するための別データである。

構造化や原文を保存しないことだけで適法性が確定するわけではない。情報解析目的の利用と、原文・類似問題を学習者へ提供する利用は区別する。法的な適用条件は [文化庁の資料](https://www.bunka.go.jp/seisaku/chosakuken/aiandcopyright.html) を参照する。

## 抽出と生成コンテキスト

1. 東北大学過去問から、教科・ジャンル・大まかな形式・知識要素の定義候補を抽出する。
2. 人間がレビューしてから、それぞれの定義テーブルへ登録する。
3. 対象試験にジャンルと形式を紐づける。原本からは定義と出題傾向の構造化データを登録し、原文は登録しない。問題キャッシュは自作・生成問題と定義への参照を持つ。
4. 対象試験を指定して、教科、対象ジャンル、対象形式、そのジャンルの知識候補を取得する。
5. 学習対象とコスト制限に合わせて知識を選び、各定義の説明と試験の制限を生成コンテキストへ入れる。
6. 生成結果を確認し、参照先・コスト制限を検証して問題キャッシュへ保存する。

抽出した分類の定義を問題ごとに複製しない。試験のジャンルに属する知識すべてが、その試験の出題範囲であるとは限らない。初版はレビューで候補を選び、必要になれば試験と知識の対応も追加する。出題頻度などの傾向は複数の問題から判断する。
