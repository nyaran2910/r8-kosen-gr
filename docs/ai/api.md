# API契約・認証設定の詳細案

[概要](../common/api.md) の認証設定・基本契約・再送と競合の扱いはユーザー確認済み。末尾の未解決事項は引き続き残す。実装しない。

## 認証

RS256、Webセッションの非利用期間24時間、APIトークン最大60秒を提案。Auth.jsセッションの更新はサーバーの対応APIで行い、Server Componentの読み取りだけでCookie更新できると仮定しない。APIトークンは署名だけで暗号化しないので不要な個人情報を入れない。秘密鍵はWeb側のみ、APIは公開鍵のみ。発行元・対象API・sub・iat・expを必須検証し、許可アルゴリズムはRS256固定。期限はWebセッションの残り期限で上限を付ける。認証用鍵の生成・配置は実装開始後。

参考：[PyJWTの署名・検証](https://pyjwt.readthedocs.io/en/stable/usage.html)、[Auth.js設定](https://authjs.dev/reference/core)。期限と構成は設計判断で、公式推奨値とはしない。

## 入出力の基本

認証主体から内部ユーザーを特定し、クライアントが所有者IDを指定するAPIは作らない。UUIDは文字列、日時はUTCのISO8601、未評価はnullとして送る。一覧はlimit既定20・最大50のカーソル方式案。成功は操作固有のJSON、エラーは `{error: {code, message, fields}, request_id}` を共通案とする。内部例外・秘密鍵・トークンをレスポンスやログへ載せない。

`feedback` 入力は `result`（perfect/correct/incorrect/gave_up）と `knowledge_feedback`（knowledge_id・understood）の配列。未入力falseと未入力の不存在を区別する。出題済み問題の知識との一致・重複・不足を検証。出力は演習ID・確定時刻・問題評価・形式理解度前後・知識評価と前後・次回復習日時。二重再送はDBの現在値ではなく確定演習に残る値を返す。復習状態が後の演習で変わっていた場合、元の確定日時から初版固定方式の予定を返すか確定時の計算結果を保存するかを具体的なレスポンス定義で詰める。未来の計算方式で再現不能になる可能性を残す。

## 再送と競合

開始時の操作IDはクライアントが一回だけ生成したUUIDを演習IDとして入力する案。サーバーは所有者と元の対象試験・問題を照合し、同一要求なら既存演習を返す。異なる要求でID再利用は409。同じユーザーの異なる操作IDが同時に開始されても再開可能な演習一つを保証する。別ユーザーのIDとの衝突は既存データを開示せず拒否する。開始時刻は表示開始通知と合わせて確定し、クライアント時刻をそのまま信用しない。

revealは初回の操作日時だけを保存し、再送は同じ状態を返す。closeは未確定のものだけ終了し、終了済みの再送は同じ結果、確定済みなら409。feedbackは終了済みを拒否し、確定済みなら同じpayloadのみ成功結果を再送する。知識配列の順序違いは同一評価とみなす。全更新をトランザクションにまとめる。

手動理解度は理解度とexpected_updated_at（未評価ならnull）を入力。現在状態の日時と合わなければ409。同一値なら実質変更なし。手動設定も操作IDを用いる案で、前回成功した要求の再送識別と同時更新条件を実装前の詳細契約で整理する。単に古い要求を新規の上書きとして扱わない。

## 状態とエラー

401は未認証、404は対象なし・他人の演習、409は競合・不可能な状態遷移、422は入力検証、503はDBや依存サービスの利用不能。次問の候補なしは200で `attempt:null`・候補なし理由・最も近いnext_review_atを返す案。認証期限切れの自動再送は更新操作へ無条件に適用しない。

廃止問題は新規開始を拒否し、廃止前に開始した本人の演習は継続できる。GETで開始・評価・復習予定を変更しない。知識・形式本文からHTMLや危険なリンクをそのまま実行しない。Next.jsの更新APIはOrigin検証・CSRF対策を具体化する。ブラウザー由来のAuthorizationを内部APIへ転送しない。
