# 学習フローの詳細コンテキスト

現行の確認用概要は [学習フロー](../common/learning-flow.md)。画面・学習フロー・中断と再開の方針はユーザー確認済み。実装禁止の指示を維持する。

## 提案の範囲と理由

試験選択・試験ホーム・演習・知識・形式・履歴を用意する。演習は問題表示から評価まで同じ画面を基本にし、解説や知識の往復で演習IDを維持する。解答入力と自動採点を追加せず、紙で解いて自己評価する初版を提案する。ユーザーが後でアプリ内解答を希望すれば見直す。

評価保存と次問開始を分ける。評価保存の成功画面で理解度の更新結果と復習予定を確認でき、次問を始めるか終了するか選べる。画面の表示は保存済みの結果を使い、クライアントで先に理解度を更新しない。保存中の連打・再送は演習IDで同じ確定結果にする。

## 演習の生存期間と未確定状態

ユーザーごとに再開可能な未確定演習を一つとする案。ホームから既存演習を再開できる。試験の閲覧や知識閲覧は別試験でも可能だが、新規演習の開始では既存演習を再開するか終了するか確認する。ユーザー指示で別試験の演習を同時進行したい場合はこの方針を変更する。

既存の `submitted_at=NULL` だけでは、中断中で再開可能な演習と、ユーザーが終了して再開しない演習を区別できない。概要確認後に `closed_at TIMESTAMPTZ NULL` など終了を表す項目を提案する。学習フローの確認に伴い `closed_at TIMESTAMPTZ NULL` をDB設計へ反映した。確定済み・終了済みの演習は新規の演習で解き直す。未確定終了は不正解や諦めたに変換しない。古い履歴を削除して終了扱いにしない。

開始・再開・終了の同時要求や複数タブでも、再開可能な演習一つの条件をDB・登録処理で守る必要がある。候補の取得時に演習を先に作らず、問題の表示開始の計測と演習作成を区別する。計測通知の通信失敗・遅延はAPI設計時に決める。端末の時計を無検証で信用しない。

## 入力途中の評価

下書きは同じタブのsessionStorageで保持する提案。キーは内部ユーザーIDと演習IDで分け、ログアウト・確定・中断演習終了で削除する。ページ復元時はサーバーから所有者と演習状態を確認し、確定済みなら古い下書きを送信せず確定結果を表示する。別ユーザーの下書きを表示しない。

sessionStorageには評価の入力だけを入れ、認証トークン・解答・教材全文を保存しない。未入力とfalseを区別する。下書きはDBの確定評価履歴へ保存しない。ブラウザーやタブを閉じた後の復元・別端末への同期は保証しない。必要ならサーバー側の下書き保存を別の設計として検討する。認証が切れた際は再ログインを案内し、他人の学習データを表示しない。

## 表示と履歴

知識一覧は教科・ジャンルで絞り、自分の理解度・未評価を表示する案。形式一覧は選択した試験に紐づく形式を表示する。手動設定は過去の評価を書き換えない。演習途中の手動変更があった場合、評価確定時はその時点の現在値に増減する既存の計算方針を使う。

履歴一覧は確定した演習を対象に、試験・問題・日時・4段階評価・回答時間を表示する。詳細では知識評価と知識・形式の理解度変化を表示する。中断演習はホームの再開入口から扱う。終了した未確定演習の一般履歴への表示は初版では省く案で、DBから消すという意味ではない。

## 次の設計

画面と中断案の承認後、終了状態のDB項目を反映し、出題順位・候補なし・履歴からの解き直しと復習期限の関係を確認する。抽出根拠の記録、初期問題数、定義訂正、手動変更履歴、認証・API詳細は未決定。まとめて設計確認する方針で進め、細部一つごとに確認を求めない。
