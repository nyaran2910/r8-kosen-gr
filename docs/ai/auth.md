# 認証の現行方針と旧案の記録

## 現行方針（2026-10-13・ユーザー確認済み）

認証をFastAPIへ集約する。Googleログイン、OIDC検証、内部ユーザー登録、セッション、本人判定、ログアウト・退会をAPIに置く。Next.jsは画面と同一オリジン中継。既存Auth.js実装はまだ削除・変更しない。

AuthlibをOAuth/OIDCクライアントの候補にする。セッションはまだ選定前。StarletteのSessionMiddlewareを使う場合、署名付きCookieは内容を暗号化しないためGoogleアクセストークンや秘密情報を入れない。ログイン中の内部IDだけを保存する方式などを検討し、OAuth state/nonce検証・Cookie属性・CSRF・期限更新をライブラリに合わせて確認する。採用バージョンを決めるときは現行公式資料で再確認する。

退会でGoogle紐づけを除去し内部IDと学習データを保持、再登録は新ID、通常アクセスでユーザーを自動作成しない方針は維持する。内部IDから現在のusersを確認し、google_subがNULLなら旧セッションを拒否する。旧案のNext.js/API二重セッション、短命署名JWT、登録通知APIは新構成の必須要件にしない。

login_registrationsは旧構成のサーバー間通知を想定した表。現行DBに存在するが、新構成で使う必要性を見直す。不要になってもユーザーの既存DBや適用済みマイグレーションを勝手に削除しない。account_deletionsと学習テーブルは認証の移動だけを理由に変更しない。

本人確認付きの更新は退会との競合制御とデータ保持方針を維持する。ログイン保持24時間は維持し、API用60秒JWTやRS256は廃止する旧案の値。初版はOAuth情報の永続保存を増やさず、必要な一時状態とアプリログイン状態を区別する。

ユーザーは自分で実装し、アシスタントには指示と確認を希望している。アプリファイルへの書き込み・依存追加・起動・DB更新は行わない。設計文書は更新する。

# 認証の検討メモ

## 確認済み

Googleログイン必須。Next.jsがログイン・セッションを管理し、FastAPIが認証済み主体を検証して `users` の内部ユーザーを特定する。学習データは内部IDへ紐づける。初版の `users` は `id` と一意の `google_sub`。担当範囲の承認は具体的なライブラリ・通信方式の承認ではない。

## ライブラリの検討方針（確認済み）

Auth.jsのNext.js用パッケージ `next-auth` は、Next.js連携とGoogleプロバイダーを提供する。Auth.jsを軸に検討する方針はユーザー確認済み。採用バージョンは未確定。公式導入手順が `next-auth@beta` を案内しているため、安定版と混同しない。バージョンは導入時に互換性と保守状況を確認して固定する。公式サイトにはBetter Authへの移行案内もあり、採用時の代替確認を残す。

## セッション方式（確認済み）

初版はAuth.jsのJWTセッションとする方針が確認済み。ログイン状態は暗号化されたトークンをHttpOnly Cookieに保存し、Next.jsが検証する。DBセッションのアダプターは追加しない構成とし、アプリの `users` と学習データは既存のPostgreSQL設計を使う。Cookieへ学習履歴・理解度・不要なプロフィール情報を入れない。

通常のログアウトはCookieの削除で行う。ただし取得済みのトークンを有効期限前に一括失効するには追加の失効管理が必要。初版では全端末一括ログアウト機能を要求しない案。非利用24時間のセッション期限は確認済み。ブラウザー側のJavaScriptからCookieを直接読ませず、localStorageにも保存しない。

JWT方式とDB方式の比較は公式資料を根拠とする。JWT方式をこの最小DB構成に合うと判断したのは設計上の提案。認証ライブラリの暗号化されたセッショントークンを、通常の署名JWTとしてFastAPIへそのまま渡せると仮定しない。API用の署名JWTの受け渡しは確認済み。内部IDとGoogle主体の照合は下記の退会対応の現行仕様に従う。

FastAPIの本人確認について、検証可能なサーバー間の認証情報・有効期限・発行元・対象APIを具体化する。任意のユーザーIDやGoogle識別子をヘッダーに載せるだけの方式は採用しない。DBユーザーの初回作成はAPI側で重複を防いで行う方針を維持する。

## Next.jsからFastAPIへの受け渡し（基本構成は確認済み）

ブラウザーは同一オリジンのNext.jsへ要求し、Next.jsサーバーがAuth.jsセッションを検証する。検証したGoogleの主体識別子を入れた短い有効期限のAPI用署名JWTを発行し、サーバー間の `Authorization: Bearer` でFastAPIへ送る案。JWTはブラウザーへ返さず、リクエストごとに必要時発行する。Auth.jsのセッションCookieはAPIへ転送しない。

FastAPIは署名・許可したアルゴリズム・有効期限・発行元・対象APIを検証し、JWTの内部IDとgoogle_sub双方の一致でユーザーを確認する。通常要求ではユーザーを作成しない。Googleに毎リクエスト問い合わせる方式ではなく、検証済みセッションに基づくNext.jsの表明を信頼する設計。

API用JWTの `sub` は内部ユーザーIDとし、別claimのgoogle_subとともに検証する。Google発行のIDトークンとは区別する。セッションの中からサーバーが保持したGoogle主体を取り出し、クライアントの更新入力で上書きさせない。有効期限はWebセッションの残り期限を超えないようにする。署名鍵はAuth.jsの暗号化用シークレットと分ける。署名方式はRS256、有効期限は最大60秒で確認済み。具体的な鍵配置は着手時に決める。

FastAPIの公式資料は署名JWT・Bearer・期限検証の実装参考。このサーバー間構成を公式がそのまま推奨しているという意味ではない。Googleログインにパスワード認証のサンプルを持ち込まない。ブラウザーからNext.jsへの更新要求は同一オリジンとCSRF対策を別途実装し、クライアントのAuthorizationヘッダーを内部APIへそのまま転送しない。

## 再登録・退会後の認証（基本動作は確認済み）

初回のユーザー作成はGoogleログインの成功を検証したNext.jsサーバーから登録用エンドポイントへ通知する。ログイン完了用の短命署名表明と通常のAPI用表明を用途・audience等で区別し、通常要求をユーザー作成の根拠にしない。登録通知の再送・同時ログインはGoogle主体の一意制約と登録操作IDで同じ内部IDを返す。退会前の遅延した登録通知が退会後に再登録を起こさないよう、登録操作結果と退会判定の扱いを実装前契約に具体化する。

成功時に内部IDをAuth.jsセッションへサーバーだけが格納する。通常のAPI用JWTのsubは内部IDとし、google_subを別claimへ持たせる新案。Google主体のみをsubとする旧案を置き換える。APIではidと非NULLのgoogle_sub一致を必須にする。クライアントのsession update入力で識別情報を差し替えさせない。

退会は本人確認済みのDELETE /meを提案。本人がデータ保持の説明を確認してから実行する。users行をロックする等で評価保存と直列化しgoogle_subをNULLにする。新規評価も状態更新も認証一致を同じ処理内で確認し、退会完了後は拒否する。users・演習・理解度は消さない。ブラウザーのCookieと下書き・個人キャッシュは破棄する。

同じGoogleで再登録したら新しいUUID。古いtokenは旧UUIDを持つので、新しいgoogle_subに一致する別usersがあっても復活しない。Google識別子から通常要求を新IDへ付け替えない。Google側の許可取消しAPIは初版では追加しない案。過去バックアップの認証紐づけ復活は別台帳と復元手順で扱う。

この確認は再登録と退会の本人側の動きの判断。署名表明のclaimスキーマ・登録再送結果保存・鍵更新など技術詳細は新案に合わせて文書を更新し、実装開始前に確認する。実装は行わない。

再登録は新内部ID、通常APIで自動作成しない、内部IDとGoogle主体の両方を照合して旧セッションを拒否する動作はユーザー確認済み。登録通知の再送識別・遅延通知拒否の内部契約は実装前に具体化する。
