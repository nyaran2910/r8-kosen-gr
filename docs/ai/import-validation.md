# 登録検証の詳細案

[3項目の概要](../common/import-validation.md) はユーザー確認済み。スキーマコード・初期データ・CLIは作らない。

## 必須項目と型

schema_versionは整数1のみ、bundle_idと全定義IDはUUID。配列名はsubjects、exams、genres、formats、knowledge_elements、exam_genres、exam_formats、problems、problem_genres、problem_knowledge。項目名を許可リストで検証し、unknown keyを拒否する。空配列は既存共有定義参照に必要で、出題対象の問題にジャンル・知識一つ以上という条件は別の参照検証で守る。

costはnullまたは有限数値、boolや数値文字列を数値として受理しない。尺度未確定なので負値などの範囲を独断で固定せず、コスト制限を使う場面では尺度確認後に検証する。retired_atはnullまたはtimezone付きISO8601。開始や学習状態はmanifestへ入れない。本文参照は登録単位内の相対パス、参照対象の正規化と脱出防止は登録形式の既存方針。

JSONの重複キーは黙って最後の値を採用せず検証で拒否する。構成・回答形式・試験区分のコード一覧は具体的な初期データ値を確定するときに整合させる。本文の説明が原本を再現するかどうかは型検証だけで決めない。

## 承認

status=approved、担当と日時、checksとfilesの整合性を検証する。レビュー記録の任意テキストだけをチェック済み扱いにせず、必須チェック項目の結果を明示する。利用条件の未解決事項をレビュー完了の記号で上書きしない。これは新たな法律判断ではなく現行legal方針の登録運用への反映。

登録対象から辿る全manifest・Markdown・配信画像・provenanceが承認filesの集合に一致し、hash一致であることを検証する。review自体はhash対象から除く。資料の原本参照は配信ファイル集合に含めずprovenanceから識別する。承認書があるだけで勝手に原本や秘密情報を配信しない。

## 差分と書き込み

読み取り検証・差分表示・明示反映を分ける。定義修正は意味不変が人の判断事項なのでCLIがtitle同一などだけで自動承認しない。問題本文・解答解説・試験形式・知識ジャンル対応は登録後別ID訂正、retired_atだけ運用状態として明示変更。既存問題の新規設定として勝手にretired_at=NULLへ戻さない。

DB内容比較は登録元ファイルのハッシュだけでなく、取り込み後の参照・本文を正規化した内容も確認する。画像取り込みとDBの反映は一つの成功単位として参照切れを避け、途中失敗の一時画像を公開しない。ローカルファイル操作までDB transactionが原子的に保証すると表現しない。

複数bundleの登録は依存順で一単位ずつ確定し、後続失敗時の既存成功単位は残す。各単位は原子的に反映する。後続を直して再実行する際も既存同内容を複製しない。errorの項目と接続先DBを表示し、秘密情報や原本全文を出さない。
